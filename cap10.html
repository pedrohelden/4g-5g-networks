Kubernetes for 4G/5G

From virtualized infrastructure to a platform capable of orchestrating telecom workloads.

Kubernetes does not replace the network architecture. It becomes the platform on which the network architecture runs.

The previous chapter established an important idea:

Modern telecom networks are increasingly implemented as software.

But software needs infrastructure.

NFVI provides the compute, memory, networking, virtualization, and hardware acceleration required to run those workloads.

The next question is obvious:

Who manages all those workloads?

In cloud-native architectures, one of the most important answers is Kubernetes.

Kubernetes provides a platform for deploying, scheduling, scaling, monitoring, and recovering containerized applications.

For telecom, however, Kubernetes cannot simply be treated as another enterprise application platform.

A 5G Core has strict networking requirements.

It may require multiple interfaces.

It may require dedicated CPU resources.

It may require deterministic networking.

It may maintain state.

It may need to survive node failures.

And some network functions may process enormous numbers of packets.

Running a web application on Kubernetes and running a 5G Core on Kubernetes are fundamentally different engineering problems.

Why Kubernetes?

Kubernetes was designed to manage containerized workloads across clusters of machines.

Instead of manually placing every application on every server, an engineer describes the desired state.

Desired State "Run three instances of this application." ``` | v Kubernetes | +------+------+ | | | v v v Pod Pod Pod ```

The platform then attempts to maintain that state.

If a pod fails, Kubernetes can create another one.

If a node fails, workloads can potentially be rescheduled elsewhere.

If capacity changes, replicas can be increased or reduced.

The engineer describes what the system should look like. Kubernetes continuously works to make reality match that description.

The Kubernetes Cluster

A Kubernetes environment is normally organized as a cluster.

Kubernetes Cluster ``` +-----------------------------------+ | | | Control Plane | | | | API Server | | Scheduler | | Controllers | | Cluster State | | | +----------------+------------------+ | +----------+----------+ | | | v v v Worker Worker Worker Node Node Node | | | Pods Pods Pods ```

The control plane is responsible for coordinating the cluster.

Worker nodes provide the resources where workloads actually execute.

The separation is conceptually important.

The control plane decides.

The worker nodes execute.

Pods

The basic execution unit in Kubernetes is the Pod.

A pod is not exactly the same thing as a container.

A pod can contain one or more containers that share networking and certain other resources.

Pod ``` +-----------------------------+ | | | Container A | | Container B | | | | Shared Network Namespace | | Shared Pod IP | | | +-----------------------------+ ```

In many simple applications, one pod contains one main container.

In telecom, additional sidecar containers may be used for logging, monitoring, configuration, security, or other supporting functions.

The pod is the fundamental networking boundary that Kubernetes presents to the application.

Pod Networking

By default, containers inside a pod share the same network namespace.

That means they can communicate through localhost.

POD ``` +-----------------------+ | | | Container A | | | | | | localhost | | v | | Container B | | | | eth0 | +----------+------------+ | v Pod Network ```

The pod normally receives a network identity from the Kubernetes networking layer.

That identity is provided through the Container Network Interface.

CNI

Container Network Interface, or CNI, is a standard used to configure networking for containers.

When a pod is created, the CNI plugin can be responsible for configuring its network connectivity.

Pod Creation | v Kubernetes | v CNI | +---- Create network namespace | +---- Create interface | +---- Assign IP | +---- Configure routes | +---- Connect to network

This makes CNI a critical component of cloud-native telecom networking.

If the CNI configuration is wrong, the application may be perfectly healthy while the network function remains unreachable.

A telecom application can be completely healthy from the process perspective and completely broken from the network perspective.

The Default Kubernetes Network

A typical Kubernetes pod starts with a primary network interface such as eth0.

Pod ``` +------------------+ | | | Network Function | | | | eth0 | | 10.x.x.x | | | +--------+---------+ | v CNI | v Kubernetes Network ```

For many enterprise applications, one interface is sufficient.

For telecom, it frequently is not.

Why Telecom Needs Multiple Interfaces

A telecom network function may need to communicate through multiple logical or physical networks.

Consider a simplified UPF.

UPF ``` +-----------------------+ | | | Control / Management | | | | eth0 | | | | | | User Plane | | | | net1 | | net2 | | | +-----------------------+ ```

The interfaces may have different purposes.

One may connect to management or signaling infrastructure.

Another may connect toward the access side.

Another may connect toward the data network.

In a 5G environment, the exact interface model depends on the network function and deployment architecture.

But the principle remains:

The network function may need to participate in multiple networks simultaneously.

Multus

This is where Multus becomes important.

Multus is a CNI meta-plugin that allows a Kubernetes pod to attach to multiple network interfaces.

Pod ``` +-------------+ | | | 5G Network | | Function | | | | eth0 | ---> Kubernetes Network | net1 | ---> Network A | net2 | ---> Network B | net3 | ---> Network C | | +-------------+ ```

The primary CNI creates the default interface.

Multus can then attach additional interfaces.

Pod | v Primary CNI | +---- eth0 | v Multus | +---- net1 +---- net2 +---- net3

This capability is extremely useful for telecom workloads.

In cloud-native telecom, networking is often not a single interface. It is a topology.

Network Namespaces

To understand multiple interfaces, it is important to understand Linux network namespaces.

A network namespace provides an isolated network environment.

It can contain its own:

  • Interfaces
  • IP addresses
  • Routing tables
  • Firewall rules
  • Network sockets
Host +-------------------------------------+ | | | Host Network Namespace | | | | eth0 | | eth1 | | routes | | | | +-------------------------+ | | | Pod Network Namespace | | | | | | | | eth0 | | | | net1 | | | | net2 | | | | routes | | | +-------------------------+ | | | +-------------------------------------+

The pod therefore has its own network view.

This is one reason a troubleshooting engineer must know how to enter a pod and inspect its network namespace.

Multiple Interfaces in Practice

Imagine a 5G network function with three interfaces.

CNF Pod ``` +------------------------+ | | | eth0 Management | | | | | +---- Kubernetes | | | | net1 Signaling | | | | | +---- Telecom Net A | | | | net2 User Plane | | | | | +---- Telecom Net B | | | +------------------------+ ```

The first question during troubleshooting should be:

Which interface carries the traffic I am investigating?

This sounds simple.

In a complex cloud-native environment, it is not.

A packet may be perfectly visible on net1 and completely absent from net2.

Looking only at eth0 may lead to the wrong conclusion.

If you capture traffic on the wrong interface, you can spend hours proving that a packet does not exist where you are simply not looking.

Services

Pods are dynamic.

Their IP addresses may change.

Applications therefore need a stable way to reach workloads.

Kubernetes provides the concept of a Service.

Service Stable Identity | +-------+-------+ | | | v v v Pod A Pod B Pod C

The service provides a stable logical endpoint while pods behind it may be created or destroyed.

For enterprise applications this abstraction is extremely useful.

For telecom, however, the engineer must understand exactly which traffic should use a Kubernetes Service and which traffic should use a specialized telecom interface.

Services and Telecom Traffic

Not every telecom packet should necessarily travel through the same networking mechanism.

A management API may use ordinary Kubernetes networking.

A service-based 5G control-plane interaction may use the pod network.

A high-performance user-plane path may require a dedicated interface.

Control Plane NF | eth0 | Kubernetes Network User Plane NF | net1 | SR-IOV / High Performance Network | Physical Network

This separation is one of the key concepts in cloud-native telecom architecture.

Deployments

A Deployment describes how Kubernetes should manage replicated stateless workloads.

Deployment | +---- Pod 1 | +---- Pod 2 | +---- Pod 3

If one pod disappears, Kubernetes can create another.

This is ideal for applications where instances are interchangeable.

For example:

  • API services
  • Stateless microservices
  • Web front ends
  • Supporting control-plane components

But telecom introduces another challenge.

Not every workload is stateless.

Stateful Applications

Some telecom functions maintain important state.

Consider session information.

UE | v Network Function | +---- Session State | +---- Subscriber Context | +---- Security Context | +---- Policy Context

If the process disappears, that state may matter.

A replacement pod cannot simply start from zero in every architecture.

This is why stateful workloads require different design considerations.

Stateless recovery means replacing a process. Stateful recovery means preserving or reconstructing the context that process was holding.

StatefulSets

Kubernetes provides StatefulSets for workloads requiring stable identity and persistent characteristics.

StatefulSet ``` | +---- Pod-0 | +---- Pod-1 | +---- Pod-2 ``` Stable identities Stable association Persistent storage where required

This is particularly useful for databases and other stateful services.

However, simply placing a telecom function in a StatefulSet does not automatically make the architecture resilient.

The application itself must support the required state-management model.

Kubernetes can restart a workload. It cannot magically reconstruct state that the application never designed to preserve.

High Availability

Telecom networks are expected to operate continuously.

A single failed server should not necessarily result in a service outage.

Service ``` +----------+ | | +--+--+ +--+--+ | NF1 | | NF2 | +--+--+ +--+--+ | | Node A Node B Failure | X | Node A | v NF2 remains operational ```

High availability therefore requires redundancy.

But redundancy must exist at multiple layers.

Application | Pod | Node | Network | Power | Rack | Site

If every replica runs on the same physical node, the deployment may appear redundant while remaining vulnerable to a single node failure.

Anti-Affinity

Kubernetes scheduling mechanisms can be used to distribute replicas across failure domains.

Bad Design Node A +---- Pod 1 +---- Pod 2 +---- Pod 3 Better Design Node A +---- Pod 1 Node B +---- Pod 2 Node C +---- Pod 3

If Node A fails in the first architecture, every replica may disappear.

In the second architecture, the workload can remain available.

Redundancy without failure-domain separation is often only an illusion of redundancy.

Readiness and Liveness

Kubernetes needs to know whether an application is alive and whether it is ready to receive traffic.

These are different concepts.

A process can be alive but not ready.

Process Running | v Application Initializing | v Database Connection | v Configuration Loaded | v Network Ready | v READY

A liveness check asks a question similar to:

Is the process still functioning?

A readiness check asks:

Can this instance safely receive traffic?

This distinction is extremely important in telecom.

A newly started network function may have a running process but may not yet have established all required connections.

Restarting a healthy-but-not-ready network function can turn a temporary initialization condition into a real outage.

Failure and Recovery

Consider a simplified failure.

UPF Pod | X Crash | v Kubernetes detects failure | v New Pod created | v CNI configures interfaces | v Network function starts | v Interfaces become ready | v Application becomes READY

This sounds straightforward.

But a telecom workload may require:

  • Multiple interfaces
  • Specific IP addresses
  • Specific routes
  • SR-IOV resources
  • Hugepages
  • Dedicated CPUs
  • NUMA placement
  • Persistent state
  • External service dependencies

The recovery process therefore becomes considerably more complex.

Scheduling Telecom Workloads

Kubernetes normally tries to place workloads where resources are available.

Telecom workloads often require more control.

A UPF might need:

UPF Requirements CPU | +---- Dedicated cores Memory | +---- Hugepages NUMA | +---- Local memory Network | +---- SR-IOV VF Topology | +---- Specific node

Kubernetes must therefore be integrated with the underlying infrastructure capabilities.

Node labels, taints, tolerations, affinity rules, resource requests, device plugins, and topology awareness can all become relevant.

Resource Requests and Limits

Kubernetes workloads can declare resource requirements.

Pod CPU Request Memory Request CPU Limit Memory Limit

This allows the scheduler to make placement decisions.

However, telecom performance engineering often requires more than simply requesting “4 CPUs.”

The engineer may care about:

  • Which CPUs?
  • Which NUMA node?
  • Shared or dedicated cores?
  • What memory locality?
  • What NIC locality?

The resource number alone is not the entire story.

Four CPUs in the wrong place are not equivalent to four CPUs in the right place.

CPU Manager and Performance

Kubernetes can be configured to support more predictable CPU allocation for workloads that require dedicated cores.

This becomes especially important for high-performance telecom functions.

Generic Workload CPU Pool +--+--+--+--+--+--+--+--+ ^ ^ ^ Flexible scheduling Telco Workload CPU Pool +--+--+--+--+--+--+--+--+ | +---- Dedicated cores | v UPF

This connects directly with the CPU pinning concepts introduced in the previous chapter.

Kubernetes does not eliminate those requirements.

It becomes the mechanism through which those requirements are expressed and enforced.

Multus and CNI Chains

Multus is particularly powerful because it can chain multiple networking components.

Pod ``` | Multus | +------------+------------+ | | | v v v CNI A CNI B CNI C | | | eth0 net1 net2 | | | Cluster Telecom A Telecom B ```

This means a pod can simultaneously participate in the Kubernetes network and in specialized telecom networks.

For example:

eth0 | +---- Service-Based Interfaces Management APIs net1 | +---- Control / Telecom Network net2 | +---- High-Speed User Plane

This architecture allows cloud-native applications to coexist with telecom networking requirements.

A 5G Core on Kubernetes

Now we can bring the concepts together.

Kubernetes Cluster ``` +---------------------------------------+ | | | AMF SMF PCF UDM | | | | | | | | Pod Pod Pod Pod | | | | UPF | | | | | Pod | | / \ | | net1 net2 | | | +---------------------------------------+ | v Physical Network ```

The 5G Core functions become cloud-native workloads.

The control plane can use service-based communication over the Kubernetes network.

The user plane can use dedicated high-performance networking.

The orchestration platform manages lifecycle and placement.

The infrastructure provides the physical resources.

5G Core | v CNFs | v Kubernetes | v CNI / Multus | v Virtual / SR-IOV Networking | v NFVI | v Physical Infrastructure

Control Plane Versus User Plane

This distinction becomes even more important in cloud-native environments.

5G Core ``` CONTROL PLANE | +---------+---------+ | | | AMF SMF PCF | | +---- SBA + | Kubernetes Network USER PLANE | UPF | High-speed interfaces | Physical NIC ```

Control-plane traffic is often dominated by signaling and API interactions.

The user plane can involve enormous packet volumes.

Therefore, the infrastructure requirements can be dramatically different.

The control plane asks the network what to do. The user plane does the work at packet scale.

State and the 5G Core

The 5G Core also introduces distributed state.

A subscriber session may involve multiple functions.

UE | v AMF | +---- Registration Context | v SMF | +---- PDU Session Context | v UPF | +---- User Plane State

The system therefore cannot be understood as a collection of independent containers.

It is a distributed system.

Each network function has responsibilities.

The interfaces between those functions become part of the application's state machine.

A cloud-native 5G Core is not simply many containers. It is a distributed telecom system whose components happen to run as containers.

High Availability in the 5G Core

Suppose an AMF instance fails.

Before ``` AMF-1 | AMF-2 | AMF-3 ``` AMF-2 fails ``` AMF-1 | X | AMF-3 ```

The remaining architecture must be capable of continuing service according to the network's design.

That requires more than Kubernetes restarting a container.

It may require:

  • Multiple replicas
  • Load distribution
  • State replication or reconstruction
  • Stable service discovery
  • Correct readiness behavior
  • Failure-aware session handling
  • Network redundancy

The orchestration platform provides mechanisms.

The telecom application must provide the actual resilience model.

High availability is an architecture, not a Kubernetes setting.

Troubleshooting a CNF

When a cloud-native network function fails, the troubleshooting process must cross layers.

User Symptom | v Telecom Protocol | v Network Function | v Container | v Pod | v Network Namespace | v CNI / Multus | v Node | v NIC | v Physical Network

This is one of the most important differences between traditional appliance-based troubleshooting and cloud-native troubleshooting.

The engineer can no longer stop at the application.

Example: AMF Cannot Reach SMF

Suppose the AMF reports that it cannot establish communication with the SMF.

The problem could exist at several layers.

AMF | +---- Application | +---- Pod | +---- eth0 | +---- CNI | +---- Kubernetes Network | +---- Service | +---- SMF Pod | +---- SMF Application

A disciplined investigation might proceed through the layers:

  • Is the AMF process running?
  • Is the AMF pod ready?
  • Does the pod have an IP?
  • Does DNS resolve the SMF service?
  • Is the route correct?
  • Can the pod reach the SMF service IP?
  • Does the service have healthy endpoints?
  • Is the SMF listening on the expected port?
  • Is traffic blocked by policy?
  • Does packet capture show the connection attempt?

The final symptom is:

“AMF cannot communicate with SMF.”

But that sentence tells us almost nothing about the root cause.

The best troubleshooting question is not “What failed?” It is “At which layer did the expected behavior stop?”

Example: UPF Has No User Traffic

Now consider a UPF that appears healthy.

UPF Pod = Running UPF Pod = Ready CPU = Normal Memory = Normal

But no user traffic is flowing.

The investigation must move toward the user-plane interface.

UE | v gNB | v Transport | v UPF net1 | v UPF net2 | v Data Network

Questions include:

  • Does the UPF have the expected interfaces?
  • Are the IP addresses correct?
  • Are routes installed?
  • Is GTP-U traffic arriving?
  • Are TEIDs correct?
  • Is the application receiving packets?
  • Are packets being dropped by the NIC?
  • Is the return route correct?

Notice how Kubernetes is only one part of the investigation.

The telecom protocol still matters.

The user plane still matters.

The physical infrastructure still matters.

Cloud-native changes where the network function runs. It does not change what the network function must accomplish.

Observability

A Kubernetes-based telecom platform should expose visibility at multiple levels.

5G Metrics | CNF Metrics | Pod Metrics | Node Metrics | CNI Metrics | NIC Metrics | Physical Network Metrics

For troubleshooting, these sources should be correlated.

For example:

14:32:01 PDU Sessions increasing | v UPF PPS increasing | v CPU utilization increasing | v RX queue increasing | v Packet drops | v User experience degradation

That is far more useful than simply looking at whether the pod is “Running.”

Running Does Not Mean Healthy

This distinction deserves emphasis.

Kubernetes State Running | X | Healthy

A pod can be running while:

  • A network interface is misconfigured
  • A route is missing
  • A dependency is unavailable
  • A service is unreachable
  • The application is internally degraded
  • Packets are being dropped
  • Sessions are failing

Kubernetes status describes the orchestration state.

It does not automatically describe telecom service health.

“Running” is a Kubernetes status. “Working” is a telecom conclusion that requires evidence.

From Kubernetes to Telecom Engineering

The real value of Kubernetes for telecom is not that it makes network functions disappear into containers.

Its value is that it provides a programmable platform for operating complex distributed systems.

It can automate:

  • Deployment
  • Scheduling
  • Scaling
  • Recovery
  • Service discovery
  • Resource allocation
  • Configuration
  • Lifecycle management

But the telecom engineer must understand what is happening underneath these abstractions.

Kubernetes ``` Automation & Orchestration | v Cloud-Native CNFs | +--------------+--------------+ | | Control Plane User Plane | | SBA / APIs GTP-U | | Kubernetes CNI Multus / SR-IOV | | +--------------+--------------+ | NFVI | Physical Network ```

The New Telecom Stack

The traditional telecom engineer could focus primarily on the network element and the protocols around it.

The modern engineer needs a broader mental model.

Service | 5G Architecture | Network Functions | Containers / CNFs | Kubernetes | CNI / Multus | Linux Networking | Virtualization / Hardware Acceleration | NFVI | Physical Network

A failure can originate anywhere in this stack.

That is why modern telecom troubleshooting requires both protocol knowledge and infrastructure knowledge.

The packet does not care whether it is running on a VM, a container, or a bare-metal server. The engineer must care.

Chapter Takeaways

Kubernetes provides orchestration for containerized workloads and maintains the desired state of the cluster.

Pods are the fundamental execution and networking unit.

Deployments are commonly used for replicated stateless workloads.

StatefulSets provide stable identity and support stateful application patterns.

Services provide stable logical endpoints for dynamic workloads.

CNI provides the networking integration between Kubernetes and the underlying network.

Multus extends this model by allowing pods to attach to multiple network interfaces.

Network namespaces isolate the network environment of workloads and define the interfaces, addresses, routes, and sockets visible to them.

Telecom workloads frequently require multiple interfaces because control, management, and user plane traffic may have different networking requirements.

High-performance workloads may require CPU pinning, NUMA awareness, hugepages, SR-IOV, and specialized networking.

High availability requires redundancy across pods, nodes, networks, and failure domains.

Most importantly, Kubernetes status must not be confused with telecom service health.

A pod can be Running while the network is broken. A node can be Healthy while the user plane is failing. A cluster can be Green while subscribers are offline.

The engineer therefore needs to correlate Kubernetes state with network protocols, packet captures, application logs, infrastructure metrics, and physical network behavior.

Cloud-native telecom is not the replacement of networking with Kubernetes. It is the integration of networking, software, orchestration, and infrastructure into one operational system.

Once this model is understood, the next challenge becomes even more interesting:

How do we connect these cloud-native functions to real telecom networks while preserving the performance, isolation, and deterministic behavior expected from carrier-grade systems?

That question leads directly into advanced container networking, CNI design, Multus, SR-IOV, service networking, high-performance data paths, and the architecture required to make cloud-native 5G operate at scale.

Linux and Cisco Troubleshooting

Command-Line Tools, System Administration and Network Diagnostics

Linux Introduction

Linux is one of the most important operating systems in modern network infrastructure. It is widely used to host applications, network functions, databases, monitoring systems, virtualized workloads, containers and cloud platforms.

For anyone working with modern communication networks, understanding Linux is therefore not only about knowing how to execute commands. It is about understanding how the operating system exposes interfaces, processes, sockets, routes, services and logs that can be used to investigate the behavior of a system.

INSIGHT

A network problem is not always a network problem. A failed connection may be caused by a missing route, a stopped service, a closed socket, a firewall rule, DNS resolution, resource exhaustion or an application failure.

Linux provides tools that allow these possibilities to be investigated layer by layer.

This chapter introduces the Linux command line with an emphasis on practical system and network investigation.

The Linux Command Line

The Linux command line provides direct access to the operating system through a shell. The most common shell is Bash (Bourne Again Shell).

A command generally follows this structure: 

command [options] [arguments]

For example: 

ip addr show eth0

In this example:

  • ip is the command.
  • addr selects the address-related functionality.
  • show requests information to be displayed.
  • eth0 identifies the interface.

Options and Arguments

Options modify how a command behaves. Arguments specify the object on which the command operates. 

ping -c 4 192.168.1.1

Here, -c 4 tells ping to send four packets, while 192.168.1.1 is the destination.

INSIGHT

Do not memorize commands as isolated strings. Learn their structure. Most Linux commands follow predictable patterns, and understanding options makes it possible to adapt them to situations you have never encountered before.

ip route

Sockets and Listening Ports

Applications communicate through sockets. A socket is associated with an IP address, transport protocol and port.

ss

The ss command displays socket statistics and is the preferred modern replacement for many uses of netstat. 

ss

ss -u
ss -l
ss -n
ss -p
ss -tulnp
  • -t — TCP sockets
  • -u — UDP sockets
  • -l — listening sockets
  • -n — do not resolve names
  • -p — show process information

A particularly useful combination is:

This shows TCP and UDP listening sockets, numeric addresses and associated processes.

INSIGHT

If an application is supposed to listen on a port but ss shows nothing, investigating routing or packet captures may be premature. The application may simply not be running or may have failed to bind to the expected socket.

Connectivity Testing

ping

Tests IP reachability using ICMP Echo messages. 

ping 192.168.1.1
ping -c 4 192.168.1.1
ping -i 0.2 192.168.1.1
ping -W 2 192.168.1.1
  • -c — number of packets
  • -i — interval between packets
  • -W — timeout for a response
  • -s — packet payload size
  • -I — select source interface or address

traceroute

Shows the path toward a destination by manipulating packet TTL values. 

traceroute 8.8.8.8
traceroute -n 8.8.8.8
traceroute -I 8.8.8.8
  • -n — disable DNS resolution
  • -I — use ICMP Echo
  • -T — use TCP probes
  • -U — use UDP probes
  • -p — destination port
INSIGHT

A failed ping does not automatically mean that the destination is unreachable. ICMP may be filtered while TCP or UDP traffic continues to work.

A Practical Linux Troubleshooting Workflow

When a service or network function is not behaving as expected, avoid jumping randomly between commands. Use a structured investigation.

Step 1 — Check the System

hostname
uptime
free -h
df -h

Step 2 — Check the Interface

ip link
ip addr

Step 3 — Check Routing

ip route
ip route get <destination>

Step 4 — Check DNS

dig <hostname>

Step 5 — Check Listening Sockets

ss -tulnp

Step 6 — Check the Process

ps aux | grep <process>
top

Step 7 — Check the Service

systemctl status <service>

Step 8 — Check Logs

journalctl -u <service> --since "15 minutes ago"

Step 9 — Test Connectivity

ping <destination>
traceroute <destination>

Step 10 — Capture Packets

tcpdump -ni <interface> host <destination>
INSIGHT

Troubleshooting becomes significantly easier when moving from lower-level dependencies toward higher-level behavior: 

System
  ↓
Interface
  ↓
IP Address
  ↓
Routing
  ↓
DNS
  ↓
Socket
  ↓
Process
  ↓
Service
  ↓
Application
  ↓
Packet Capture

This is not a rigid rule. It is a mental framework for avoiding unnecessary assumptions.

Practical Scenario: An Unreachable Service

Assume an application should be reachable at: 

192.168.20.50:8080

A structured investigation could begin with: 

ping 192.168.20.50

If the host responds, check the route: 

ip route get 192.168.20.50

Then verify whether the application is listening: 

ss -lntp | grep :8080

If nothing is listening, inspect the process: 

ps aux | grep application

Then inspect the service: 

systemctl status application

And finally inspect recent logs: 

journalctl -u application --since "10 minutes ago"

If the service appears healthy, capture the traffic: 

tcpdump -ni any host 192.168.20.50 and port 8080

The capture can reveal whether packets arrive, whether responses are generated and whether the TCP connection is successfully established.

INSIGHT

The objective of troubleshooting is not to execute as many commands as possible. The objective is to progressively eliminate possible causes until the remaining explanation is supported by evidence.

Architecture, hardware families, CLI, routing, IP/MPLS, and integration with 4G/5G networks

Routers are often introduced as devices that connect different IP networks. That definition is technically correct, but it is insufficient for understanding how routers operate in enterprise networks, service provider backbones, data centers, and mobile networks.

A production router is a complex distributed system. It learns topology and reachability information, calculates paths, applies routing policies, builds forwarding structures, classifies traffic, enforces security policies, participates in redundancy mechanisms, and ultimately forwards packets at very high rates.

For a network engineer, therefore, learning router configuration is only one part of the job. The more important skill is understanding why a router makes a particular forwarding decision and how to prove whether that decision is correct.

Insight: It is not a good idead to troubleshoot by randomly trying commands until something changes. The engineer builds a hypothesis, collects evidence, eliminates possible causes, and only then changes the configuration.

Chapter Objectives

By the end of this chapter, the reader should be able to understand Cisco routers as network engineering platforms rather than simply as devices that accept CLI commands.

  • Understand the role of routers in enterprise, service provider, data center, and mobile network architectures.
  • Recognize the major Cisco platform families, including ISR, Catalyst, ASR 1000, ASR 9000, NCS, and Nexus.
  • Understand the basic Cisco IOS/IOS XE CLI model and recognize important differences in IOS XR and NX-OS.
  • Configure and troubleshoot interfaces, IPv4, IPv6, static routes, OSPF, IS-IS, BGP, VRFs, VLANs, subinterfaces, ACLs, NAT, QoS, and high-availability mechanisms.
  • Understand the relationship between IP routing, MPLS, VRF-based services, and mobile transport networks.
  • Relate router troubleshooting to 4G and 5G signaling and user-plane traffic.
  • Develop a structured troubleshooting methodology that begins with physical connectivity and progresses toward routing, transport, tunnels, and applications.

The Router Inside the Network

A router forwards packets between different IP networks. At the most basic level, the process is straightforward: a packet arrives on an interface, the router determines where the destination prefix should be reached, and the packet is transmitted through the appropriate outgoing interface toward the next hop.

The important engineering question is what happens before that packet arrives.

The router must learn which networks exist, determine which paths are available, evaluate routing information, select preferred routes, resolve next hops, and build forwarding structures that can be used efficiently for every packet. 


+----------------------+ 
|      NETWORK A       |
|    10.10.10.0/24     |
+----------------------+
           |
+----------------------+
|       ROUTER R1      |
+----------------------+
           |
+----------------------+
|      NETWORK B       |
|    10.20.20.0/24     |
+----------------------+

Packet destination: 10.20.20.25
R1 determines:
    Destination prefix  -> 10.20.20.0/24
    Next hop            -> appropriate path
    Outgoing interface  -> appropriate interface

The router does not need a complete list of every host in the destination network. It primarily needs sufficient reachability information to determine the correct forwarding path.

Key Concept: Routing is fundamentally about reachability and path selection. Forwarding is the act of applying that decision to individual packets.

A Router Is Not Synonymous with the Internet

The same fundamental forwarding principle exists in a small enterprise LAN, a carrier-grade IP/MPLS backbone, a data center fabric, and the transport network of a 4G or 5G mobile operator.

What changes is the scale and complexity: the number of routes, protocols, interfaces, VRFs, policies, tunnels, redundancy mechanisms, traffic classes, and availability requirements.

Operational Impact: A routing failure in a small office may affect a few users. The same logical failure in a mobile operator's aggregation or core network can affect thousands or millions of subscribers and multiple services simultaneously.

Control Plane and Forwarding Plane

One of the most important concepts in modern routers is the separation between the control plane and the forwarding plane.

The control plane is responsible for learning and calculating network information. It runs routing protocols, maintains adjacencies, processes routing updates, and determines which paths should be used.

The forwarding plane takes the resulting information and applies it to packets. Its objective is extremely different: instead of calculating topology, it must perform packet lookups and forwarding decisions at very high speed.

Impact: A routing protocol failure and a forwarding-plane failure are not necessarily the same problem. A router may still have valid routing information while experiencing packet loss caused by hardware, interface, queue, ACL, or forwarding-resource problems.
Senior Engineer Insight: When troubleshooting, always ask: "Is the router unable to calculate the path, or does it know the path but fail to forward the packet?" This distinction immediately narrows the troubleshooting domain.

RIB, FIB, and the Forwarding Decision

The Routing Information Base (RIB) contains routing information learned from different sources, such as connected networks, static routes, OSPF, IS-IS, and BGP.

The Forwarding Information Base (FIB) is the optimized structure used by the forwarding plane to make packet-forwarding decisions.

These concepts are related, but they are not interchangeable. 

Routing Sources

The RIB is concerned with routing knowledge and route selection. The FIB is concerned with forwarding execution. A route may be present in routing information without being usable for forwarding, for example when its next hop cannot be resolved or when platform-specific conditions prevent installation.

A Structured Troubleshooting Methodology

One of the most common troubleshooting mistakes is beginning with the most sophisticated protocol in the architecture.

For example, if a mobile service is experiencing packet loss, an engineer might immediately inspect BGP, GTP, or application signaling. But if the physical interface has CRC errors, all of that higher-level investigation may be irrelevant. 

1. PHYSICAL
   Cable / optics / power / interface

          ↓

2. LAYER 2
   VLAN / trunk / MAC / ARP

          ↓

3. LAYER 3
   IP / mask / gateway / routing

          ↓

4. ROUTING
   OSPF / IS-IS / BGP / policy

          ↓

5. SECURITY
   ACL / firewall / NAT

          ↓

6. TRANSPORT
   TCP / UDP / SCTP

          ↓

7. TUNNEL / SERVICE
   GTP-U / GTP-C / IPsec / MPLS

          ↓

8. APPLICATION
   DNS / HTTP / SIP / APIs
Senior Engineer Insight: The exact order can change depending on the symptom, but the principle remains: use evidence to move upward through the stack instead of guessing at higher-layer causes.
Practical Rule: Do not abandon lower-layer evidence simply because the problem appears to involve a sophisticated protocol. A BGP session reset may ultimately be caused by an unstable physical link. A GTP-U failure may ultimately be caused by an incorrect route. A SIP failure may ultimately be caused by an MTU problem.

Interview Questions

What is the difference between RIB and FIB?

The RIB contains routing information; the FIB is the optimized structure used for packet forwarding.

OSPF or BGP?

OSPF is normally used as an IGP within a routing domain. BGP is a policy protocol used between Autonomous Systems and also widely used in internal architectures of service providers.

Ping works, but the application does not. What do you do?

Identify the application's protocol and ports, verify routing and the complete path, check ACLs, firewalls, NAT, MTU, and QoS, and then perform a protocol-specific test. Working ICMP does not end the diagnosis.

How would you investigate BGP down?

Start with IP reachability, TCP/179 state, remote address and AS, update source and multihop where applicable, authentication, and logs. Then investigate policies and resource constraints.

How would you investigate a GTP-U problem?

Separate control plane from user plane, confirm transport IP addresses, routing and CEF, verify UDP/2152 where applicable, ACLs, MTU, QoS, and capture traffic if necessary.

What is a VRF?

A VRF is a logical separation of routing tables that allows independent routing domains to coexist on the same device.

Closing

Routers are the infrastructure that transforms a collection of isolated networks into a system capable of transporting services end-to-end. In a small network, this may mean a few interfaces and a simple routing table. In a service-provider network, it means thousands of paths, multiple VRFs, IGP, BGP, MPLS, policies, QoS, and high-availability mechanisms.

For an engineer working close to 4G and 5G networks, understanding routers in depth is especially important because the mobile core depends on predictable IP infrastructure. When a mobile session fails, the problem may be in signaling, the user plane, or the transport between network functions. Routing knowledge makes it possible to separate these possibilities and reach the root cause using evidence.

Final Engineering Principle: The competency that differentiates an experienced engineer is not knowing a larger number of commands. It is knowing which question needs to be answered, which command provides the evidence, and how to connect that evidence to the actual behavior of the service.

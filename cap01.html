Chapter 1: Fundamentals of Mobile Networks and End-to-End Architecture

A modern mobile network is not a single system and it is not simply a radio network. It is a large distributed infrastructure in which radio access, Ethernet, IP routing, transport networks, signaling protocols, packet forwarding, subscriber databases, cloud platforms, security controls, and external data networks must operate together as one end-to-end service.

From the perspective of a subscriber, the experience appears simple: connect to the network and access a service. From the perspective of a network engineer, however, that apparently simple operation may involve dozens of network functions, multiple protocol layers, several physical locations, redundant paths, tunnels, routing domains, and control-plane transactions.

This difference between the user's view and the network's internal complexity is one of the most important ideas in mobile network engineering.

A failure experienced by the subscriber as "the Internet is not working" may originate in the radio access network, VLAN configuration, IP routing, transport connectivity, a signaling association, subscriber authentication, a GTP tunnel, a firewall, NAT, DNS, an external network, or even the destination application itself.

The objective of this chapter is therefore not simply to introduce mobile network components. Its purpose is to establish an end-to-end engineering mental model that can be used throughout the rest of this book.

By the end of this chapter, the reader should be able to look at a mobile network problem and reason from the subscriber device down to the physical network and back toward the application, identifying where the expected behavior stops.

The Foundations of Mobile Networking

Understanding the Network as an End-to-End System

A mobile network can be understood as a distributed communication system that connects a User Equipment (UE) to a service through several logical and physical domains.

A simplified representation is: 

UE
 |
 | Radio Access
 v
RAN
 |
 | IP Transport
 v
Mobile Core
 |
 | Data Network
 v
Internet / Enterprise / IMS / Application

Every arrow in this diagram represents more than physical connectivity. It represents a combination of interfaces, addressing, routing, transport protocols, signaling procedures, security mechanisms, and operational state.

For example, a working Ethernet link between two devices does not necessarily mean that an IP route exists. An IP route does not guarantee that an SCTP association can be established. An SCTP association does not guarantee that application signaling will succeed. Successful signaling does not guarantee that user-plane traffic will be forwarded.

This creates a fundamental engineering principle:

Connectivity at one layer does not prove connectivity at the next layer.

The same principle applies in the opposite direction. If an application fails, it does not automatically mean that the application itself is broken. The application may simply be the first component capable of revealing a lower-layer failure.

Why Mobile Networks Are Different from Traditional IP Networks

Traditional IP networks are primarily concerned with forwarding packets between endpoints. Mobile networks must solve a much broader problem.

A mobile network must know who the subscriber is, whether that subscriber is authorized, where the subscriber is currently attached, which services are permitted, which IP address should be assigned, which quality-of-service rules should apply, and where subscriber traffic should be forwarded.

The network must also maintain this state while the subscriber moves between cells, potentially between tracking areas, and sometimes between different access technologies.

This means that mobile networking combines traditional IP engineering with telecommunications-specific concepts such as:

  • Subscriber identity.
  • Authentication and authorization.
  • Mobility management.
  • Session management.
  • Bearer and QoS management.
  • Packet tunneling.
  • Policy enforcement.
  • Charging.
  • Interworking between network generations.
  • Roaming.

A senior mobile network engineer therefore needs to be comfortable moving between telecom architecture and conventional networking concepts.

Evolution of Mobile Networks

Mobile networks have evolved through several generations. Each generation increased capacity, introduced new services, and progressively increased the importance of packet networking and software-based infrastructure.

Although the architecture changed significantly from 2G to 5G, several fundamental requirements remained constant:

  • Identify the subscriber.
  • Authenticate the subscriber.
  • Provide access to the network.
  • Manage mobility.
  • Establish connectivity.
  • Forward traffic.
  • Apply policy and QoS.
  • Maintain service availability.

Understanding this continuity is useful because many concepts introduced in earlier generations evolved rather than disappeared.

2G — Digital Cellular Networking

Second-generation systems introduced large-scale digital cellular communication. GSM became one of the most widely deployed mobile technologies in the world.

The architecture separated radio access from the core network and introduced dedicated functions for mobility management, authentication, subscriber databases, and circuit-switched services.

Initially, data services were relatively limited. The network was primarily designed around voice and signaling rather than high-speed IP connectivity.

The introduction of GPRS and later EDGE changed this model by adding packet-switched data capabilities.

This was a major architectural transition because mobile networks began carrying IP traffic as a native service rather than treating data as an exception to a primarily circuit-switched architecture.

Several concepts that became central to 3G, 4G, and 5G therefore have their roots in this period:

  • Packet gateways.
  • Subscriber addressing.
  • Mobility management.
  • Packet tunneling.
  • Packet-based charging.
  • Separation between control and traffic handling.

3G — Increasing Packet Orientation

Third-generation systems increased radio capacity and enabled more advanced data services. UMTS continued the separation between radio access and core network functions while significantly improving packet-based connectivity.

The packet core provided access to external packet networks while mobility management, authentication, and subscriber databases continued to coordinate subscriber access.

From an engineering perspective, 3G represents an important transition toward the packet-oriented architectures that would become dominant in LTE.

4G LTE — The IP-Centric Mobile Network

LTE represented a major architectural transformation.

The radio access network evolved into E-UTRAN, based primarily on the eNodeB, while the packet core evolved into the Evolved Packet Core (EPC).

Unlike previous generations, LTE was designed around an almost entirely packet-based architecture.

Traditional circuit-switched voice was no longer part of the LTE packet core. Voice could instead be delivered through the IP Multimedia Subsystem (IMS), including Voice over LTE (VoLTE).

The EPC introduced several network functions that became fundamental to mobile packet networking:

  • MME — Mobility Management Entity, responsible for control-plane mobility and session-related procedures.
  • SGW — Serving Gateway, providing user-plane forwarding and mobility anchoring within the EPC.
  • PGW — Packet Data Network Gateway, providing connectivity toward external packet networks.
  • HSS — Home Subscriber Server, containing subscriber information and supporting authentication-related procedures.
  • PCRF — Policy and Charging Rules Function, providing policy and charging control.

LTE also established extensive use of IP transport and tunneling. GTP became a fundamental mechanism for transporting subscriber traffic, while SCTP became important for signaling transport on interfaces such as S1-MME.

For network engineers, LTE therefore represents an important point where telecommunications and conventional IP networking become deeply interdependent.

5G — Software-Oriented and Service-Based Architecture

5G introduced another major architectural evolution.

The 5G Core (5GC) was designed around a Service-Based Architecture (SBA). Instead of relying exclusively on traditional point-to-point interfaces, network functions expose services that can be consumed by other network functions.

Important 5G Core functions include:

  • AMF — Access and Mobility Management Function.
  • SMF — Session Management Function.
  • UPF — User Plane Function.
  • PCF — Policy Control Function.
  • UDM — Unified Data Management.
  • AUSF — Authentication Server Function.
  • NRF — Network Repository Function.
  • NSSF — Network Slice Selection Function.
  • NEF — Network Exposure Function.
  • UDR — Unified Data Repository.

The architecture also increases the separation between control-plane decision-making and user-plane packet forwarding.

This separation enables operators to place user-plane functions closer to subscribers and applications while keeping control functions centralized or distributed according to operational requirements.

Another major change is the increasing use of virtualization and cloud-native infrastructure.

Network functions can be implemented as Virtual Network Functions (VNFs) or Cloud-Native Network Functions (CNFs), running on general-purpose compute platforms.

As a result, a mobile network engineer increasingly needs to understand not only routers and telecom protocols, but also virtualization, containers, Kubernetes, service discovery, observability, Linux networking, and distributed systems.

The Major Domains of a Mobile Network

User Equipment

User Equipment (UE) represents the subscriber endpoint.

The UE may be a smartphone, mobile broadband modem, industrial device, vehicle, router, IoT endpoint, or another cellular device.

From the network perspective, the UE is more than an IP endpoint. It contains subscriber-related identities and participates in radio and signaling procedures required to obtain service.

Once connectivity has been established, the UE may receive an IPv4 address, an IPv6 prefix, or both, depending on the network configuration and requested service.

Radio Access Network

The Radio Access Network (RAN) provides the radio interface between the UE and the operator network.

In LTE, the principal radio access element is the eNodeB. In 5G New Radio, the corresponding element is the gNodeB.

The RAN performs functions such as:

  • Radio resource management.
  • Scheduling.
  • Radio bearer handling.
  • Mobility procedures.
  • Radio measurements.
  • Connection management.
  • Communication with the mobile core.

However, the RAN should not be treated as an isolated radio environment. The connection between a radio node and the core is usually transported over an IP-based network.

Consequently, a problem that appears to be a radio problem may actually be caused by transport connectivity between the RAN and the core.

Transport Network

The transport network connects geographically distributed mobile network elements.

It may contain Ethernet switches, IP routers, optical transport systems, aggregation networks, synchronization infrastructure, and data-center connectivity.

A typical transport architecture may resemble: 

Radio Site
    |
    | Ethernet
    v
Access Network
    |
    v
Aggregation

    v
IP/MPLS Transport
    |
    v
Core / Data Center

Transport infrastructure is particularly important because a single failure can affect many services simultaneously.

A broken link to one subscriber is usually a localized problem. A failed aggregation router can potentially affect hundreds of cells and thousands of subscribers.

Typical transport responsibilities include:

  • Layer 2 connectivity.
  • Layer 3 routing.
  • Traffic engineering.
  • Quality of Service.
  • Redundancy.
  • Path protection.
  • Network synchronization.
  • Inter-site connectivity.
  • Data-center connectivity.

Mobile Core

The mobile core provides the centralized or distributed functions required to control subscriber access and connectivity.

Depending on the generation and architecture, the core may be responsible for:

  • Authentication.
  • Mobility management.
  • Session management.
  • Subscriber data.
  • Policy enforcement.
  • IP address allocation.
  • User-plane forwarding.
  • Charging.
  • Interworking.
  • Connectivity toward external networks.

The core is therefore where subscriber identity and network connectivity become tightly coupled.

External Data Networks

The mobile network usually does not terminate subscriber traffic. Instead, the traffic is forwarded toward an external destination.

Possible destinations include:

  • The public Internet.
  • Enterprise networks.
  • Private applications.
  • IMS services.
  • Operator-hosted services.
  • Cloud platforms.
  • Other interconnected networks.

This boundary is particularly important during troubleshooting.

A mobile core may successfully forward a subscriber packet to an external router, while the external network fails to return the packet.

Therefore, end-to-end troubleshooting must continue beyond the mobile operator's own infrastructure whenever the evidence requires it.

Architecture Is Logical, Not Necessarily Physical

One of the most important concepts for engineers working with modern networks is the distinction between logical functions and physical devices.

A logical network function does not necessarily correspond to one physical appliance.

For example, a 5G Core function may run as a software workload on a virtual machine or container platform. Multiple network functions may share the same physical server while remaining logically independent.

Similarly, one physical platform may host several logical interfaces and network functions.

This means that troubleshooting must consider both views:

  • Logical view — network functions, interfaces, sessions, protocols, and relationships.
  • Physical view — servers, NICs, switches, routers, links, CPUs, memory, and data-center infrastructure.

A failure may therefore cross both dimensions.

For example, a PDU Session may appear to fail at the SMF level while the underlying cause is a network-interface problem on the Kubernetes node hosting the relevant workload.

This relationship between telecom functions and infrastructure becomes increasingly important as the book progresses into cloud-native mobile networks.

Control Plane and User Plane

The Most Important Concept in Mobile Troubleshooting

One of the most important concepts in mobile network engineering is the distinction between the control plane and the user plane.

The two planes are related, but they solve different problems.

The control plane establishes and maintains the state required for communication. The user plane carries the subscriber's actual traffic.

Control Plane

The control plane is responsible for signaling, decisions, state establishment, and coordination between network functions.

Typical control-plane operations include:

  • Registration.
  • Authentication.
  • Mobility management.
  • Session establishment.
  • Bearer establishment.
  • Policy decisions.
  • Subscriber authorization.
  • Network-function discovery.
  • Session modification and release.

The control plane can therefore be thought of as the mechanism that tells the network what should exist.

For example, before subscriber packets can flow through a 5G UPF, the network must establish the appropriate session and forwarding state.

User Plane

The user plane carries the subscriber's actual payload.

Examples include:

  • Web traffic.
  • Video streaming.
  • Application traffic.
  • Voice media.
  • VPN traffic.
  • IoT data.
  • Enterprise traffic.

In LTE and 5G, GTP-U is commonly used to encapsulate subscriber packets across the mobile transport network. 

Subscriber IP Packet
        |
        v
      GTP-U
        |
        v
       UDP
        |

        IP
        |
        v
     Ethernet

The outer packet belongs to the mobile transport network, while the encapsulated packet belongs to the subscriber.

This distinction is critical during packet analysis.

Control Plane Working Does Not Guarantee User Plane Working

A common troubleshooting mistake is to assume that successful session establishment proves that subscriber connectivity is working.

It does not.

A subscriber may successfully:

  • Detect the cell.
  • Register.
  • Authenticate.
  • Establish a session.
  • Receive an IP address.

And still be completely unable to reach the Internet.

The failure may occur after the control plane has completed its work. Potential causes include:

  • Missing routing.
  • Incorrect forwarding state.
  • Broken GTP-U tunnels.
  • Firewall policies.
  • NAT problems.
  • MTU mismatches.
  • External network failures.
  • Asymmetric routing.

This gives the engineer a powerful diagnostic boundary:

If control-plane state is confirmed but user traffic fails, move the investigation toward the data path.

The Reverse Situation

The opposite can also occur.

The underlying IP network may be operational while the control plane is unable to establish service.

For example: 

Ethernet       SUCCESS
    |
IP routing     SUCCESS
    |
SCTP           SUCCESS
    |
S1AP signaling FAILURE
    |
Subscriber     NO SERVICE

In this situation, checking physical links repeatedly is unlikely to find the root cause because the lower-layer evidence already demonstrates that basic connectivity exists.

The investigation should move upward toward the signaling protocol, configuration, state, and subscriber procedures.

The Engineer's Key Question

When investigating a mobile network failure, one of the most useful questions is:

Is the network failing to establish the required state, or is the established state failing to forward traffic?

The first situation usually points toward the control plane.

The second usually points toward the user plane or the external data path.

This distinction can reduce an investigation involving hundreds of network elements to a much smaller and more manageable failure domain.

The engineer should not necessarily inspect every layer in every incident. Instead, the investigation should use evidence to determine where to focus.

If an interface is physically down, there is little value in beginning with application-level analysis.

The goal is not to follow a checklist mechanically. The goal is to use layered reasoning to eliminate failure domains efficiently.

Ethernet and Layer 2 Fundamentals

MAC Addresses

Ethernet uses MAC addresses to identify interfaces within a Layer 2 broadcast domain.

Switches maintain MAC address tables to determine where Ethernet frames should be forwarded.

A problem at this level can prevent IP connectivity even when Layer 3 configuration appears correct.

Examples include incorrect switching configuration, missing MAC learning, port problems, or traffic being placed into the wrong Layer 2 segment.

VLANs

Virtual LANs provide logical Layer 2 segmentation.

Operators may use VLANs to separate different categories of traffic, depending on the network design.

Examples can include:

  • Management traffic.
  • Control-plane traffic.
  • User-plane traffic.
  • Synchronization traffic.
  • Operations and maintenance traffic.

The exact segmentation strategy varies between operators and deployment models.

An incorrect VLAN configuration can produce symptoms that appear at higher layers as routing or signaling failures.

MTU

The Maximum Transmission Unit (MTU) defines the largest IP packet that can normally be transmitted without fragmentation on a Layer 3 interface.

Mobile networks frequently use encapsulation and tunneling. Every additional header consumes part of the available packet size.

This creates a common failure pattern: 

Small packets       ---> SUCCESS

Large packets       ---> FAILURE

Cause may be:
MTU / fragmentation / filtering

MTU problems can be especially difficult because basic connectivity tests may succeed while real application traffic fails.

This is particularly relevant to GTP tunnels, VPNs, IPv6, cloud-native networking, and paths involving multiple encapsulation layers.

Advanced Networking Concepts for Mobile Engineers

Why IP Networking Is Fundamental to Mobile Networks

Modern mobile networks cannot be understood as isolated telecom systems. Although radio and mobile-core protocols define subscriber behavior, the majority of the infrastructure connecting these functions is based on Ethernet and IP networking.

A mobile network engineer therefore needs to understand traditional networking concepts at the same depth required to understand telecom signaling. A failure in a routing table, VLAN, MTU, interface, firewall, or transport path can appear to the mobile-core engineer as a signaling or subscriber problem.

For example, consider an LTE eNodeB that cannot establish an S1-MME connection with the MME. The immediate symptom may appear to be a failure of LTE signaling. However, the actual cause could be:

  • A failed physical interface.
  • An incorrect VLAN.
  • A missing IP address.
  • An incorrect subnet mask.
  • A missing route.
  • An incorrect next hop.
  • A firewall rule.
  • An unreachable MME address.
  • An SCTP association failure.
  • An incorrect S1AP configuration.

The telecom protocol is therefore only one layer of the investigation. The engineer must determine at which layer the expected behavior stops.

The End-to-End Layer Model

A useful engineering model is to visualize mobile connectivity as a stack of dependencies. 

Application
    |
Service / DNS
    |
TCP / UDP
    |
IP
    |
GTP / Telecom Tunneling
    |
Ethernet / VLAN
    |
Physical / Optical / Radio Transport
    |
Hardware / Virtual Infrastructure

Higher layers depend on the correct operation of lower layers. Consequently, an application failure does not necessarily mean that the application itself is defective.

For example, if a subscriber cannot access an HTTPS service, the engineer should not immediately investigate TLS or the application server. The problem may be caused by a missing route, DNS failure, packet loss, NAT, GTP tunnel failure, or an unreachable UPF.

The opposite is also true. If every lower layer has been validated, continuing to investigate routing may provide no additional value.

The objective is therefore not to investigate every layer indefinitely, but to identify the smallest layer and failure domain consistent with the available evidence.

A common failure mode is asymmetric routing, in which the packet reaches the destination successfully but the response follows an invalid or unexpected path.

For example, a subscriber may send traffic through UPF-A while the return traffic is routed toward UPF-B. If the subscriber state exists only on UPF-A, the return packet may be discarded.

This is particularly important in environments containing:

  • Multiple UPFs.
  • Redundant gateways.
  • Load balancers.
  • Multiple data centers.
  • Geographically distributed cores.
  • Cloud networking.
  • Multiple Internet exits.

Therefore, packet-path analysis should always consider both directions.

Routing Decisions

A router does not understand the subscriber's application context when making a normal IP forwarding decision. It primarily evaluates the destination IP address against its forwarding information.

Consider a simplified routing table: 

Destination        Next Hop
--------------------------------
0.0.0.0/0          10.10.10.1
10.20.0.0/16       10.10.10.2
10.20.30.0/24      10.10.10.3

If a packet is destined for 10.20.30.25, the /24 route is more specific than the /16 or default route and is therefore preferred.

This principle is known as longest-prefix match.

Understanding this behavior is essential when investigating mobile networks because subscriber pools, management networks, transport networks, and external data networks often overlap with multiple routing domains.

This is why return routing is particularly important when subscriber addresses are private or when multiple NAT and firewall domains are involved.

Network Address Translation

Network Address Translation (NAT) allows private IP addresses to be translated into other addresses, frequently public addresses used to access the Internet.

In mobile networks, large subscriber populations may share public IPv4 addresses through Carrier-Grade NAT (CGNAT).

NAT introduces another stateful component into the packet path. Troubleshooting therefore needs to consider not only routing but also translation state.

Typical NAT-related problems include:

  • Exhausted public addresses.
  • Port exhaustion.
  • Missing translation entries.
  • Incorrect routing toward the NAT device.
  • Firewall policies.
  • Session timeout behavior.
  • Asymmetric routing.

A packet capture before and after NAT can be particularly valuable because the source address and source port may change between observation points.

Stateful Network Functions

Some network functions make forwarding decisions based not only on packet headers but also on connection or session state.

Examples include:

  • Firewalls.
  • NAT gateways.
  • Load balancers.
  • Packet gateways.
  • UPFs.
  • Policy enforcement systems.

This creates an important troubleshooting distinction.

A router may be able to forward a packet using only a routing table, while a stateful firewall may require an existing session entry before allowing the packet to pass.

Consequently, a ping failure or TCP connection failure cannot always be explained by routing alone.

+----------------------+
|       Ethernet       |
+----------------------+

The original subscriber packet may have been generated assuming a particular MTU. After encapsulation, the outer packet becomes larger.

If an intermediate network cannot transport the resulting packet, several different behaviors may occur depending on the protocol and configuration:

  • Fragmentation.
  • Packet fragmentation being blocked.
  • ICMP messages indicating an MTU limitation.
  • Silent packet drops.
  • Application-level timeouts.

This can create one of the most deceptive classes of network problems: small packets work while larger packets fail.

Packet Loss and Retransmission

Packet loss does not necessarily appear as an immediate total outage. Applications may continue functioning while performance progressively degrades.

TCP can compensate for packet loss through retransmission, but this recovery introduces additional latency and reduces effective throughput.

For example: 

Packet 1  ---> received
Packet 2  ---> received
Packet 3  ---> LOST
Packet 4  ---> received
Packet 5  ---> received

TCP detects missing data
        |
        v
Retransmission
        |
        v
Additional delay

Therefore, a network can appear operational while still delivering poor subscriber experience.

This distinction is important when separating availability from performance.

Latency and Jitter

Latency represents the time required for traffic to travel between endpoints or network functions.

Jitter represents variation in packet delay.

Both are relevant to mobile services, particularly real-time applications such as voice, video, interactive services, and industrial applications.

A network may therefore have:

  • Low packet loss but excessive latency.
  • Acceptable latency but high jitter.
  • High throughput but poor responsiveness.
  • Good average performance but severe short-duration congestion.

A senior engineer should therefore avoid using a single metric as a complete representation of network health.

Signaling as a State Machine

Why Signaling Must Be Understood as State

Telecom signaling is not simply a sequence of independent packets. Signaling procedures create and modify state across multiple network functions.

For example, a successful mobile session may require coordinated state across: 

UE
 |
 | Registration
 v
RAN
 |
 | Signaling
 v
Control Plane
 |
 | Session Establishment
 v
User Plane
 |
 | Packet Forwarding
 v
External Network

If one component believes that a session exists while another component does not have the corresponding state, traffic can fail even though individual interfaces remain operational.

Control Plane State vs User Plane State

This distinction is especially important in LTE and 5G.

A control-plane procedure can successfully establish a session while the user-plane forwarding state remains incorrect or incomplete.

For example, in 5G: 

UE
 |
 | Registration
 v
AMF
 |
 | PDU Session Establishment
 v

 |

UPF
 |

Each stage creates or modifies state.

If the PDU Session is reported as established but the corresponding UPF forwarding rules are missing, the subscriber may receive an IP address while still being unable to exchange traffic.

Transaction Correlation

Large mobile networks generate enormous quantities of signaling. Troubleshooting therefore requires correlation between events.

Useful identifiers may include:

  • Subscriber identifiers.
  • Session identifiers.
  • TEIDs.
  • IP addresses.
  • Transaction identifiers.
  • Correlation identifiers.
  • Network-function identifiers.
  • Timestamps.

A single subscriber transaction may generate messages across several network functions. The engineer must correlate these events rather than analyzing each message independently.

TEIDs and Tunnel Correlation

Tunnel Endpoint Identifiers (TEIDs) are fundamental to GTP-based user plane analysis.

A GTP tunnel can be represented conceptually as: 

Endpoint A                         Endpoint B

10.10.1.10                         10.10.2.10
     |                                  |
     | GTP-U                            |
     | TEID 0x12345678                  |
     +--------------------------------->|
                                        |
                                  Subscriber
                                  Packet

The outer IP addresses identify the transport endpoints, while the TEID helps identify the logical tunnel context.

During packet analysis, the engineer can use TEIDs to correlate packets with a specific subscriber session or bearer context, depending on the architecture.

Packet Capture Strategy

Capturing everything everywhere is rarely an efficient troubleshooting strategy.

A better approach is to define a hypothesis and capture the interfaces that can confirm or reject it.

For example, if the hypothesis is that a packet reaches the UPF through N3 but does not leave through N6, the most valuable capture points are:

Wireshark and TShark

Protocol analysis tools such as Wireshark and TShark provide different ways of examining network traffic.

Wireshark is particularly useful for interactive analysis, protocol decoding, filtering, stream reconstruction, and visual inspection.

TShark provides command-line packet analysis and is useful for automation, remote troubleshooting, large captures, and integration with scripts.

A practical workflow can be:

The tool itself does not replace engineering knowledge. Packet captures provide evidence; the engineer must interpret that evidence in the context of the network architecture.

Operations in Production Mobile Networks

Monitoring vs Troubleshooting

Monitoring and troubleshooting are related but distinct activities.

Monitoring attempts to continuously determine whether the network is healthy and whether predefined thresholds or abnormal conditions exist. Troubleshooting begins when an abnormal behavior requires investigation.

A mature operational environment combines:

  • Real-time monitoring.
  • Historical metrics.
  • Alarm management.
  • Log aggregation.
  • Packet analysis.
  • Configuration management.
  • Change management.
  • Incident management.

Alarms Are Evidence, Not Conclusions

An alarm identifies an abnormal condition, but it does not necessarily identify the root cause.

For example, a large number of downstream alarms may all be consequences of a single transport failure. 

Core Router Failure
        |
        +---- RAN alarms
        |
        +---- SCTP alarms
        |
        +---- Session failures
        |
        +---- Subscriber complaints
        |
        +---- Application failures

If each alarm is investigated independently, engineers may incorrectly treat symptoms as separate incidents.

Correlation is therefore essential.

Change Management

A significant percentage of production incidents occur shortly after a configuration, software, routing, or infrastructure change.

A useful troubleshooting question is:

What changed immediately before the problem started?

Potential changes include:

  • Router configuration.
  • Firewall policies.
  • Routing policies.
  • Network-function upgrades.
  • Cloud deployments.
  • New VLANs.
  • New IP prefixes.
  • DNS changes.
  • Security policies.
  • Software releases.

Temporal correlation does not prove causality, but it provides a valuable starting point for investigation.

Blast Radius

The concept of blast radius is useful for understanding the potential scope of a failure.

A failure affecting one interface has a different operational impact from a failure affecting a shared router, data center, routing domain, or centralized core function.

A practical classification can be: 

Single Subscriber
       |
Single Cell
       |
Site / Cluster
       |
Region
       |
Core Domain
       |
National Network

The larger the affected population, the more likely it becomes that the failure involves shared infrastructure.

Capacity and Resource Exhaustion

Not every network failure is caused by incorrect configuration. Infrastructure can also fail because resources become exhausted.

Potential bottlenecks include:

  • CPU.
  • Memory.
  • Network bandwidth.
  • Packets per second.
  • Connection tracking entries.
  • NAT ports.
  • Storage.
  • Queues and buffers.
  • Virtual CPU allocation.
  • Cloud network limits.

Resource exhaustion can create intermittent or progressive failures, making it significantly harder to diagnose than a complete interface failure.

Control Plane Scaling

Mobile networks must support large numbers of subscribers and signaling transactions.

A network may therefore have sufficient bandwidth while still becoming overloaded by signaling transactions.

Examples include:

  • Large registration storms.
  • Massive device reconnect events.
  • Mobility storms.
  • Repeated authentication failures.
  • Network recovery after an outage.
  • Software faults generating excessive signaling.

This demonstrates why bandwidth alone is not an adequate measure of network capacity.

User Plane Scaling

User-plane capacity is influenced by more than interface bandwidth. Packet processing rate is also critical.

A system forwarding large packets may achieve high throughput while struggling with very high packet-per-second rates.

Conversely, small packets can create significant processing overhead even when total bandwidth remains relatively low.

This becomes particularly important in cloud-native packet-processing environments where CPU efficiency, memory access, virtualization overhead, and network acceleration directly influence performance.

Cloud-Native Mobile Networking

From Appliances to Software

Traditional mobile networks were heavily based on dedicated hardware appliances. Modern 4G and especially 5G architectures increasingly use software-based network functions.

A simplified evolution can be represented as: 

Dedicated Hardware
       |
       v
Virtualized Network Function
       |
       v
Cloud-Native Network Function
       |
       v
Distributed Cloud Infrastructure

This evolution changes the skill set required from network engineers. Understanding routers and telecom protocols remains essential, but engineers must also understand virtualization, Linux, containers, Kubernetes, cloud networking, observability, and automation.

Virtual Machines and Containers

A virtual machine provides an abstraction of physical hardware through a hypervisor. Containers provide process-level isolation while sharing the host operating system kernel.

A simplified representation is: 

Physical Server
       |
   Hypervisor
       |
+------+------+------+
| VM 1 | VM 2 | VM 3 |
+------+------+------+

Containerized environments instead resemble:

          |

          |
   +------+------+------+
   | C1   | C2   | C3   |
   +------+------+------+

5G Core network functions may be deployed using these approaches depending on the operator architecture and vendor implementation.

Kubernetes and Network Functions

Kubernetes provides orchestration capabilities for containerized applications and is increasingly relevant to cloud-native telecom deployments.

However, packet-processing network functions introduce requirements that are not typical of ordinary web applications.

These requirements may include:

  • High packet-processing performance.
  • Deterministic resource allocation.
  • Low latency.
  • High network throughput.
  • CPU isolation.
  • NUMA awareness.
  • High-performance networking.
  • Multiple network interfaces.

This is why cloud-native telecom infrastructure often requires technologies such as SR-IOV, DPDK, Multus, CPU pinning, hugepages, and NUMA-aware scheduling.

Service-Based Architecture

5G introduced a Service-Based Architecture in which network functions communicate through services rather than relying exclusively on the point-to-point interfaces traditionally associated with earlier mobile architectures.

A simplified representation is:

This approach increases software flexibility but also introduces additional dependencies such as service discovery, API communication, certificates, DNS, HTTP/2, and cloud networking.

HTTP/2 and 5G Core

Many 5G Service-Based Architecture interactions use HTTP/2 over TCP. This creates a bridge between traditional telecom signaling and modern software engineering concepts.

An engineer troubleshooting a 5G Core therefore may need to investigate:

A service failure can therefore originate from either the telecom function itself or from the underlying software and networking stack.

Senior-Level Diagnostic Scenarios

Scenario: Registration Works, Internet Fails

Suppose a 5G subscriber successfully completes registration and receives an IP address but cannot access the Internet.

The initial conclusion should not be "5G is broken."

The evidence already indicates that several functions are operational. 

5G Cell Detection        SUCCESS
Registration             SUCCESS
Authentication           SUCCESS
PDU Session              SUCCESS
IP Assignment            SUCCESS
Internet Access          FAILURE

The investigation should therefore prioritize:

  • N3 GTP-U traffic.
  • UPF forwarding state.
  • PFCP configuration.
  • N6 routing.
  • Firewall policy.
  • NAT.
  • Return routing.
  • MTU.
  • External connectivity.

Scenario: One Site Cannot Attach

Suppose thousands of subscribers at one site cannot attach, while neighboring sites operate normally.

The scope immediately suggests that the failure may be associated with the site or its transport path.

The engineer should investigate:

  • Site connectivity.
  • VLAN configuration.
  • IP addressing.
  • Routing.
  • SCTP connectivity.
  • S1 configuration.
  • Synchronization.
  • Recent site changes.

Because the failure is geographically localized, investigating a national core outage first would be inefficient unless independent evidence points in that direction.

Scenario: Only Large Packets Fail

Suppose small ICMP packets succeed but larger packets fail.

This pattern should immediately raise suspicion of MTU or fragmentation problems.

The investigation should compare:

  • Packet sizes.
  • Interface MTUs.
  • Encapsulation overhead.
  • Path MTU.
  • Fragmentation behavior.
  • ICMP filtering.
  • VPN or tunnel overhead.

Scenario: Packets Leave the UPF but Never Return

Suppose a packet capture confirms that subscriber traffic leaves the UPF toward the external network, but no response returns.

The investigation should move beyond the UPF.

Chapter 1 — Engineering Principles

Principle 1: Follow the Packet

The most reliable way to understand a network problem is to follow the packet through the architecture.

If you know where the packet is, where it came from, where it is supposed to go, and where it disappears, you are already close to the root cause.

Principle 2: Separate Control Plane from User Plane

A subscriber can successfully register while user traffic remains broken. Always determine whether the network failed to establish state or failed to use an established state for packet forwarding.

Principle 3: Scope the Problem Before Changing Anything

The number of affected subscribers, sites, regions, services, or protocols is valuable diagnostic information.

Do not lose this information by immediately changing configurations. First understand the blast radius.

Principle 4: Interfaces Define Investigation Boundaries

Every network interface represents a potential point of observation. When traffic exists on one side but not on the other, the failure domain becomes significantly smaller.

Principle 5: Evidence Beats Assumptions

A device being "up" does not prove that traffic is being forwarded. A session being "established" does not prove that the user plane works. An interface being operational does not prove that routing is correct.

Always validate the behavior that matters.

Principle 6: Consider the Return Path

Forward traffic reaching its destination does not guarantee successful communication. Return routing, NAT, firewall state, and asymmetric paths must also be considered.

Principle 7: Think in Layers

When troubleshooting, move between: 

Physical
   |
Layer 2
   |
Layer 3
   |
Transport
   |
Telecom Signaling
   |
Tunnel
   |
Subscriber IP
   |
Application

A failure at one layer can manifest as a symptom at another.

Principle 8: Understand Dependencies

Modern mobile networks depend on more than traditional telecom functions. DNS, routing, virtualization, Kubernetes, cloud infrastructure, certificates, databases, APIs, and security systems may all affect subscriber connectivity.

Principle 9: Validate Before and After Changes

Every production change should have a defined expected result and a verification procedure.

This creates a direct relationship between engineering activity and observable network behavior.

Principle 10: The Goal Is the Failure Boundary

The ultimate objective of troubleshooting is not to run as many commands as possible.

The objective is to determine:

What is working, what is not working, and exactly between which two known-good points the expected behavior disappears.

Once that boundary is identified, the investigation becomes much more focused and the probability of finding the root cause increases dramatically.

Final Engineering Perspective

A mobile network should be viewed as one distributed system rather than as a collection of independent technologies.

The radio network provides access, the transport network provides connectivity, the mobile core establishes subscriber state and policy, the user plane forwards traffic, and external networks provide access to applications and services.

Every layer depends on the layers beneath it, while every higher-level service ultimately depends on the successful operation of the complete end-to-end path.

For a senior engineer, the ability to move between these layers is more important than memorizing isolated commands or protocol definitions.

The engineer should be able to start with a subscriber symptom and work backward through the architecture: 

Subscriber Symptom
        |
        v

At each stage, the engineer asks the same fundamental question:

What evidence proves that this part of the network is working?

This mindset transforms troubleshooting from a process of guessing into a process of elimination based on observable evidence.

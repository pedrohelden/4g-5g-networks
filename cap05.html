Troubleshooting EPC and User Plane

From subscriber symptoms to packet evidence, tunnel state, and root cause.

A network problem is rarely where the symptom appears.

In the previous chapters, we learned how LTE is built and how its signaling procedures create the state required for subscriber connectivity.

Now we move into the part of network engineering where architecture knowledge becomes practical: troubleshooting.

A subscriber reports that the Internet is not working. A VoLTE call has no audio. A device shows full radio signal but cannot establish a data session. A bearer exists, but packets are disappearing. A GTP tunnel appears healthy, yet the application cannot reach its destination.

These symptoms are easy to describe. The difficult part is determining exactly where the failure occurs.

That is the difference between checking a network and troubleshooting a network.

Troubleshooting is not the art of guessing what is broken. It is the discipline of proving where the failure begins.

Start With the Symptom, Not the Component

One of the most common mistakes in telecom troubleshooting is starting with a favorite network element.

An engineer sees a subscriber without Internet access and immediately checks the PGW. Another sees an attach failure and immediately restarts the MME. Someone sees packet loss and immediately blames the transport network.

This approach is dangerous because the first component investigated is often chosen by intuition rather than evidence.

A better approach starts with the observable symptom.

Observed Symptom | v What exactly is failing? | v At what stage does it fail? | v Which message should appear next? | v Was that message observed? | v Where does the expected behavior stop? | v Which network boundary owns that failure?

The objective is to reduce uncertainty one step at a time.

The fastest troubleshooting path is usually the one that eliminates the largest number of possibilities with the smallest amount of evidence.

The End-to-End Path

Before opening Wireshark, looking at logs, or checking counters, reconstruct the subscriber's expected path.

UE | | LTE-Uu v eNodeB | | S1-MME v MME | | S11 v SGW | | S5/S8 v PGW | | External IP v Router / Firewall | v Internet

The return path is equally important.

Internet | v Router / Firewall | v PGW | v SGW | v eNodeB | v UE

This immediately creates a powerful troubleshooting question:

Where can the packet disappear?

It can disappear at the radio interface. It can fail to reach the eNodeB. It can fail to cross S1-U. It can be incorrectly mapped to a bearer. It can be lost at the SGW. It can fail on S5/S8. It can reach the PGW and then fail because of routing, policy, firewall, DNS, or external connectivity.

Every hop is a hypothesis. Every capture point can turn a hypothesis into evidence.

Divide the Problem Into Planes

Before diving into individual protocols, determine whether the problem is primarily related to the control plane or the user plane.

Subscriber Problem | +----------+----------+ | | Control Plane User Plane | | Can UE attach? Can packets flow? Authentication? S1-U? Bearer setup? GTP-U? Session creation? S5/S8? | Routing? | NAT? | DNS? | Firewall?

This simple separation can dramatically reduce the troubleshooting scope.

If the UE cannot authenticate, investigating Internet routing is premature.

If authentication and bearer establishment succeed but no GTP-U traffic is observed, the investigation should move toward the user plane.

If GTP-U reaches the PGW but the original IP packet never leaves toward the external network, the problem is probably beyond the tunnel itself.

Do not troubleshoot the Internet when the subscriber has not yet reached the Internet.

Finding the First Broken Step

Suppose a subscriber reports:

“I have LTE coverage, but mobile data does not work.”

That statement is not yet a diagnosis. It contains almost no information about where the failure occurs.

We need to decompose it.

  • Does the UE have radio connectivity?
  • Does the UE send an Attach Request?
  • Does the MME receive it?
  • Does authentication succeed?
  • Does security activation complete?
  • Does the PDN session get created?
  • Is the default bearer established?
  • Are GTP-U tunnels present?
  • Does the UE have an IP address?
  • Can the UE reach the gateway?
  • Does DNS resolve?
  • Can packets reach the Internet?
  • Do return packets come back?

Each answer removes entire classes of possible causes.

The best troubleshooting question is the one that divides the problem space.

Reading S1AP and NAS for Evidence

When a subscriber cannot attach, S1AP and NAS are often the first places to investigate.

The eNodeB and MME communicate using S1AP over SCTP. NAS messages between the UE and MME are transported through this signaling relationship.

A simplified sequence may look like:

UE eNodeB MME | | | |-- Attach Request ->| | | |-- Initial UE Msg ->| | | | | |<-- Downlink NAS ---| |<-- Authentication -| | | | | |-- Authentication ->| | | |------------------->| | | | | |<-- Security / NAS -| | | | | |<-- Context Setup -| |<-- Radio Context --| |

The key question is not simply whether S1AP packets exist.

The key question is: which expected message was the last successful message?

If an Attach Request is observed but no Authentication Request follows, the failure is already localized significantly.

If authentication succeeds but no session establishment follows, the investigation moves further into EPC session management.

The last successful message is often more valuable than the first error message.

SCTP: The Transport Layer You Cannot Ignore

S1AP depends on SCTP. Therefore, an S1AP problem may actually be a transport problem.

When investigating S1 signaling, verify:

  • SCTP association establishment
  • Source and destination IP addresses
  • SCTP port 36412
  • Association state
  • Packet loss or retransmissions
  • Routing between eNodeB and MME
  • Firewall or ACL behavior

A failed SCTP association can prevent higher-level S1AP signaling from existing at all.

eNodeB | | SCTP Association | +----------------------+ | MME If SCTP fails: SCTP X | S1AP X | NAS transport X

This is an example of dependency-based troubleshooting.

If the transport layer is broken, searching for an application-layer signaling problem may waste hours.

Always verify that the lower layer can carry the upper layer before blaming the upper layer.

GTP-C: Did the Network Build the Session?

Once attach and authentication are successful, the investigation often moves toward GTP-C.

GTP-C is used to establish and modify session and bearer state between EPC components.

The important question becomes:

Did the network actually create the state required for user-plane forwarding?

MME SGW PGW | | | |-- Create Session ->| | | |-- Create Session ->| | | | | |<-- Response -------| |<-- Response -------| | | | |

A missing or rejected Create Session procedure can prevent user-plane connectivity even when the UE has successfully authenticated.

At this point, useful investigation areas include:

  • APN configuration
  • Serving gateway selection
  • PDN gateway selection
  • Subscriber subscription data
  • IP address allocation
  • Bearer parameters
  • Cause values in GTP-C responses
  • Policy interactions
  • Routing toward the selected gateway

Bearers: The State Behind the Traffic

A user-plane packet does not simply enter the EPC and hope that a gateway figures out where it belongs.

The network maintains bearer state.

That state links the subscriber session with the radio and core forwarding paths.

A simplified model looks like this:

Subscriber Session | +---- Default Bearer | +---- Bearer Context | +---- eNodeB tunnel | +---- SGW tunnel | +---- PGW context

When the bearer state is inconsistent between nodes, packets can be lost even though the individual components appear operational.

For example, an eNodeB may send GTP-U traffic using a TEID that the SGW no longer recognizes.

Or the SGW may forward traffic toward a PGW using an outdated tunnel context.

A tunnel can be operational at one endpoint and broken from the perspective of the session.

TEIDs: Following the Tunnel

The Tunnel Endpoint Identifier, or TEID, is one of the most useful fields when investigating GTP-U.

A TEID identifies the logical tunnel context used by a GTP endpoint.

S1-U eNodeB | | GTP-U | TEID 0x12345678 v SGW | | GTP-U | TEID 0xABCDEF01 v PGW

Notice that the TEID does not necessarily remain identical across every interface. Different tunnel legs can have different identifiers.

Therefore, an engineer should correlate the control-plane information that established the tunnel with the user-plane TEIDs observed in packet captures.

This is especially useful when a packet is seen on one interface but not another.

If you cannot correlate the user-plane packet with the correct tunnel context, you are not yet troubleshooting the session — you are only observing traffic.

GTP-U: Is the Packet Actually Moving?

Once the bearer and tunnel context exist, the next question is simple:

Are GTP-U packets actually flowing?

A typical user-plane path may look like:

UE | | Original IP packet v eNodeB | | GTP-U v SGW | | GTP-U v PGW | | Original IP packet v Internet

A capture taken on S1-U will normally show the original subscriber packet encapsulated inside GTP-U.

A capture on the PGW's external interface may instead show the subscriber packet without the GTP encapsulation.

This difference allows us to compare packet visibility across interfaces.

The Two-Capture Method

One of the most powerful techniques in packet troubleshooting is to capture traffic on two sides of the suspected failure point.

Capture A Capture B eNodeB =================== SGW =================== PGW S1-U S5/S8 ``` Packet seen A? Packet seen B? YES NO | +---- Failure likely between A and B ```

This is much stronger evidence than saying:

“Packets seem to be dropping.”

If the same logical traffic is clearly visible before a network boundary and absent after it, the investigation can focus on that boundary.

The same principle can be applied at the PGW:

GTP-U side External side PGW | | Capture A | +----------------+ | | Capture B | External Router

If GTP-U packets arrive at the PGW but the corresponding IP packets do not leave toward the external network, the problem is no longer an S1-U problem.

Packet captures turn “somewhere in the network” into a measurable boundary.

Wireshark as a Telecom Tool

Wireshark becomes particularly powerful when the engineer understands the architecture behind the packets.

Useful filters can include:

s1ap nas-eps sctp gtp gtpv2 gtp.teid ip.addr == x.x.x.x udp.port == 2123 udp.port == 2152

The exact protocol dissector names can vary depending on the capture and Wireshark version, so filters should always be validated against the actual decoded packet fields.

The important idea is to filter by function rather than simply scrolling through thousands of packets.

For example:

  • SCTP can reveal transport problems below S1AP.
  • S1AP can reveal signaling between eNodeB and MME.
  • NAS-EPS can reveal attach and mobility procedures.
  • GTP-C can reveal session establishment.
  • GTP-U can reveal actual subscriber traffic.
The value of Wireshark does not come from displaying packets. It comes from allowing you to test a hypothesis against packet-level evidence.

TShark: Automation for Large Captures

When captures become large, manually inspecting them becomes inefficient.

This is where TShark becomes extremely useful.

TShark allows packet analysis to be integrated into scripts and repeatable troubleshooting procedures.

Instead of manually searching through a multi-gigabyte capture, an engineer can extract specific protocols, fields, IP addresses, TEIDs, timestamps, or error conditions.

For example, a troubleshooting workflow can extract:

  • All GTP-U packets for a TEID
  • All GTP-C Create Session procedures
  • All S1AP messages for a specific subscriber context
  • All packets associated with a particular IP address
  • Retransmissions and transport errors
  • First and last packet timestamps

This turns packet analysis into something repeatable.

A good troubleshooting tool should reduce the time between a question and the evidence needed to answer it.

IP Connectivity: The Tunnel Can Be Healthy While the Network Is Broken

One of the most dangerous assumptions in EPC troubleshooting is:

“GTP-U is working, therefore the Internet must be working.”

That is not necessarily true.

GTP-U only proves that encapsulated traffic is moving through a particular tunnel path. It does not prove that the original IP packet can successfully reach its destination.

After decapsulation at the PGW, conventional IP networking becomes critical.

Mobile Core UE | | GTP-U v PGW | | Decapsulated IP v Routing Table | +---- Firewall | +---- NAT | +---- Default Route | v External Network

Possible failures include:

  • Missing routes
  • Incorrect next-hop configuration
  • Asymmetric routing
  • Incorrect NAT
  • Firewall filtering
  • ACLs
  • MTU problems
  • ARP or neighbor-resolution problems
  • Incorrect VRF

This is where telecom troubleshooting meets traditional IP engineering.

The packet does not stop being an IP packet just because it spent part of its journey inside GTP.

DNS: When the Network Works but Applications Do Not

A subscriber can have working IP connectivity and still report that “the Internet is not working.”

DNS is one of the first things to investigate in such cases.

Consider:

UE | | DNS Query v DNS Resolver | | DNS Response v UE | | TCP / TLS / HTTP v Destination

If DNS resolution fails, applications that depend on domain names may appear completely broken even when basic IP connectivity is healthy.

Useful tests include checking whether:

  • The UE receives the expected DNS server addresses
  • DNS queries leave the subscriber network
  • Responses return
  • UDP/53 or TCP/53 traffic is permitted when required
  • IPv4 and IPv6 DNS behavior is consistent
  • The configured resolver is reachable

This distinction is critical:

“No website opens” does not automatically mean “there is no IP connectivity.”

DHCP and Address Configuration

In many IP networks, engineers naturally think about DHCP when a host needs an address. LTE subscriber addressing is different in important ways, because the EPC manages subscriber session and IP allocation as part of PDN connectivity.

The UE can receive an IP address as part of the session establishment process rather than using ordinary Ethernet-style DHCP for the initial mobile data session.

Nevertheless, DHCP can still appear in mobile environments for specific services, enterprise deployments, local networks, tethering scenarios, or other infrastructure functions.

The important troubleshooting principle is therefore not:

“Every IP problem must be a DHCP problem.”

Instead, ask:

Who is responsible for assigning this particular address, and at which layer is that assignment supposed to happen?

Do not apply a familiar troubleshooting model to the wrong architecture.

MTU and Fragmentation

MTU problems are particularly interesting in mobile networks because encapsulation adds overhead.

An original IP packet may fit within an endpoint's expected MTU but become problematic when additional headers are introduced by tunneling.

Original packet +-----------------------------+ | IP + Payload | +-----------------------------+ After tunneling +--------------------------------------+ | Outer IP | UDP | GTP-U | Inner IP | +--------------------------------------+ ↑ Additional overhead

Symptoms can include:

  • Some websites work while others do not
  • Small packets succeed but large packets fail
  • TCP connections establish but stall during data transfer
  • Fragmentation appears unexpectedly
  • Path MTU Discovery fails
  • ICMP messages are filtered

These failures are often difficult to recognize because basic ping tests may succeed.

A network can pass small packets perfectly and still be fundamentally broken for real applications.

Return Traffic: The Forgotten Half of Troubleshooting

Engineers frequently focus on the outbound packet.

But communication requires a return path.

UE | | Request v Internet | | Response v UE

A subscriber may successfully send packets toward the Internet while responses are lost on the way back.

Possible causes include:

  • Missing return route
  • Incorrect NAT
  • Asymmetric routing
  • Firewall state mismatch
  • Incorrect PGW configuration
  • Incorrect GTP-U tunnel mapping
  • Transport network problems

This is why two-way packet captures are so valuable.

If you only prove that the request leaves, you have proved only half of the connection.

A Complete End-to-End Troubleshooting Method

A disciplined investigation can follow the subscriber's packet through the architecture.

Subscriber reports problem | v Confirm exact symptom | v Check UE / radio state | v Check S1AP / NAS | v Check authentication | v Check GTP-C | v Check bearer state | v Check TEIDs | v Check GTP-U | v Check PGW decapsulation | v Check IP routing | v Check NAT / firewall | v Check DNS | v Check return path | v Identify first broken boundary | v Root Cause

The sequence is not rigid. Experienced engineers will often jump directly to the most informative evidence.

But the underlying logic remains: start from the symptom and progressively reduce the possible failure domain.

Building a Timeline

Time is one of the most powerful dimensions available in packet analysis.

A subscriber procedure can be reconstructed chronologically:

10:00:01.001 Attach Request 10:00:01.015 Authentication Request 10:00:01.041 Authentication Response 10:00:01.060 Security Mode Command 10:00:01.071 Security Mode Complete 10:00:01.102 Create Session Request 10:00:01.145 Create Session Response 10:00:01.201 Initial Context Setup 10:00:01.250 First GTP-U packet

If the expected Create Session Response is missing, the timeline immediately highlights the problem.

If the first GTP-U packet never appears, the investigation can focus on the state immediately before user-plane activation.

If GTP-U begins but stops seconds later, the problem may be associated with tunnel state, mobility, policy, transport, or an external dependency.

A packet capture is not just a collection of packets. It is a timestamped history of network decisions.

Correlation Is More Important Than Volume

Large telecom networks generate enormous amounts of data. Logs, counters, traces, packet captures, alarms, and monitoring systems can easily overwhelm an engineer.

More data does not automatically mean more understanding.

The objective is to correlate the same subscriber and the same session across multiple systems.

Subscriber Identity | +---- MME context | +---- eNodeB context | +---- Bearer ID | +---- GTP TEID | +---- UE IP address | +---- PGW session | +---- Application traffic

When these identifiers are correlated, the distributed network begins to look like one coherent system.

The breakthrough in difficult troubleshooting often comes when separate pieces of evidence are proven to belong to the same session.

From Symptom to Root Cause

Consider a practical example.

The subscriber reports no Internet connectivity.

The UE is attached. Authentication succeeded. The default bearer exists. GTP-C session establishment succeeded. GTP-U packets are visible on S1-U. The same traffic reaches the PGW.

At the PGW external interface, however, the corresponding packets never appear.

At this point, continuing to investigate the eNodeB would be irrational.

The evidence has already moved the failure domain toward the PGW's external processing path: routing, firewall, NAT, policy, VRF, interface state, or another function between the GTP-U decapsulation point and the external network.

UE | | GTP-U YES v eNodeB | | YES v SGW | | YES v PGW | | NO X External Network Likely failure domain: PGW forwarding / routing / policy / NAT / firewall

This is what a real troubleshooting conclusion should look like.

Not:

“The network is dropping packets.”

But:

“GTP-U traffic reaches the PGW, but the corresponding decapsulated IP traffic is not observed on the external interface. The failure is therefore localized to the PGW forwarding path or downstream connectivity.”
Good troubleshooting does not merely identify what is broken. It defines the boundary beyond which the problem cannot be.

What Experienced Engineers Do Differently

Experienced engineers are not necessarily better because they know more commands.

They are often better because they ask better questions.

They avoid changing multiple variables simultaneously.

They preserve evidence before restarting components.

They compare a failing session with a known-good session.

They correlate timestamps across nodes.

They understand the expected call flow before interpreting an abnormal one.

They distinguish symptoms from causes.

And most importantly, they do not confuse activity with health.

A system producing packets is not necessarily a healthy system. A healthy system is one producing the packets it should produce, at the time it should produce them, with the state it should maintain.

Known-Good Versus Failing Sessions

One of the most effective techniques in telecom troubleshooting is comparison.

Capture a working subscriber and compare it with the failing subscriber.

WORKING FAILING Attach YES YES Authentication YES YES Bearer YES YES GTP-C YES YES GTP-U YES YES PGW external IP YES NO | v Investigate here

This approach dramatically reduces noise.

Instead of trying to understand everything that happened, the engineer asks:

What is different between the successful and unsuccessful cases?

The answer often points directly toward the failure.

The Troubleshooting Mindset

There is a temptation in complex networks to search for a single broken component.

But many failures are caused by inconsistencies between components.

A tunnel may exist on one node but not another. A route may exist in one VRF but not another. A policy may be installed but not enforced. A bearer may exist but use an incorrect identifier. A DNS server may be reachable but return unusable information.

The network can therefore appear healthy when each component is examined independently. The failure only becomes visible when the components are viewed together.

The hardest network problems often live between systems, not inside them.

Chapter Takeaways

Troubleshooting LTE is fundamentally an exercise in reconstructing state and following traffic.

Start with the subscriber's exact symptom. Do not assume which component is responsible.

Separate control-plane problems from user-plane problems.

Use S1AP and NAS to understand access, mobility, authentication, and signaling.

Use SCTP to verify the transport foundation of S1AP.

Use GTP-C to determine whether session and bearer state was successfully created.

Use bearer information and TEIDs to correlate logical subscriber sessions with actual tunnels.

Use GTP-U to determine whether subscriber traffic is physically moving through the mobile core.

Once traffic is decapsulated, return to the fundamentals of IP networking: routing, NAT, firewalling, VRFs, MTU, ARP, and return paths.

Treat DNS as an application dependency rather than assuming every application failure is an IP connectivity failure.

Understand where IP addressing is actually provided in the architecture instead of automatically assuming DHCP.

Use Wireshark and TShark not simply to inspect packets, but to test specific hypotheses.

Capture traffic at multiple points whenever possible.

Correlate subscriber identity, bearer identifiers, TEIDs, IP addresses, timestamps, and logs.

TROUBLESHOOTING MODEL ``` Symptom | v Expected Behavior | v Call Flow | v First Missing Step | v Failure Domain | v Evidence | v Root Cause | v Fix | v Verification ```
Do not stop when you find the symptom. Do not stop when you find the failed packet. Stop when you can explain why the packet failed, where it failed, and why the evidence proves it.

That is the difference between monitoring a network and engineering a network.

The EPC is a distributed system. Its failures are distributed as well. The engineer's job is to reconstruct the path, identify the state, follow the evidence, and reduce the problem until only one plausible failure domain remains.

When you can explain the packet's journey, you can explain the failure.

In the next chapter, we will move beyond the LTE EPC and into the architecture of 5G Core, NSA, and SA — where the principles remain familiar, but the architecture becomes significantly more distributed, service-based, and cloud-oriented.

The technology changes. The engineering method remains: understand the expected path, observe the real path, and find the first place where they diverge.

4G Signaling and Call Flows

From radio access to authentication, bearer establishment, mobility, and voice services.

A mobile network does not simply connect a device. It negotiates, authenticates, establishes, maintains, moves, and eventually releases a subscriber's state.

In the previous chapter, we built the architectural map of the LTE Evolved Packet Core. We identified the UE, eNodeB, MME, HSS, SGW, PGW, and PCRF, and we learned how interfaces such as S1-MME, S1-U, S11, S5/S8, S6a, and Gx connect them.

But architecture alone does not explain behavior.

A diagram can tell us that the MME is connected to the HSS. It does not tell us when the MME contacts the HSS, why it does so, what information is exchanged, or what happens if one of those messages fails.

That is where signaling and call flows become essential.

A call flow is effectively the timeline of a mobile network operation. It shows which node initiates an action, which node responds, which protocol carries the message, and what state changes as a result.

If architecture tells you where everything is, signaling tells you why everything is there.

Thinking in Signaling States

One of the most important ideas in LTE troubleshooting is that a subscriber is not simply "connected" or "disconnected."

The network maintains multiple layers of state.

The UE has radio state. The MME maintains mobility and NAS state. The eNodeB maintains radio and access-side context. The SGW and PGW maintain bearer and tunnel state. The HSS maintains subscriber information. Policy functions maintain service rules.

A failure can therefore occur after one part of the process succeeds but before another part has completed.

For example, a UE may successfully establish radio connectivity but fail authentication. It may authenticate successfully but fail to establish a default bearer. It may establish the default bearer but later lose the user-plane path.

A successful procedure is not one successful message. It is a chain of states that must remain consistent.

NAS, S1AP, SCTP, and GTP: The Signaling Stack

Before following the attach procedure, it is important to understand the protocols involved. LTE signaling is layered, and the same signaling event can involve several protocols at different levels.

UE | | NAS | eNodeB | | S1AP | MME | | GTP-C | SGW | | GTP-C | PGW

NAS, or Non-Access Stratum signaling, is used between the UE and the core network for procedures such as mobility management and session management.

S1AP, the S1 Application Protocol, operates between the eNodeB and MME. It transports signaling associated with the radio access and core-network relationship and can carry NAS messages between the UE and MME.

SCTP, the Stream Control Transmission Protocol, provides the transport layer for S1AP.

GTP-C is used inside the EPC for session and bearer control, particularly between the MME, SGW, and PGW.

GTP-U is used for the actual subscriber user-plane traffic.

When reading a packet capture, never look at the protocol in isolation. Ask which network function is using it and what state that message is trying to create or change.

The Attach Procedure

The LTE attach procedure is one of the most important call flows in the entire architecture. It is the process through which a UE registers with the EPC and establishes the context required for packet-data connectivity.

A simplified view looks like this:

UE eNodeB MME HSS | | | | |-- Attach Request ->| | | | |-- Initial UE Msg ->| | | | |-- Auth Req ---->| | | |<-- Auth Info ----| | |<-- Authentication ->| | |<-- Authentication -| | | | | | | | | |---- Session ----| | | | Setup | | | | | | |<-- Initial Context Setup ----------| |<-------------------| | | | | | | |========== Default Bearer / User Plane ===================|

The real procedure is considerably more detailed, but this simplified flow provides the correct mental model.

The UE begins by requesting access. The eNodeB transports the request toward the MME. The MME identifies the subscriber context it needs, authenticates the UE, establishes security, coordinates session creation, and ultimately causes the necessary bearer and forwarding state to be installed.

Only after these steps have succeeded does the subscriber have a complete path for normal packet traffic.

Attach Request: The Conversation Begins

The procedure begins with an Attach Request from the UE.

The UE provides information that allows the network to identify the subscriber and understand the requested access procedure.

The message is transported through the eNodeB using the S1AP framework toward the MME.

UE | | NAS Attach Request v eNodeB | | S1AP Initial UE Message v MME

This is an important distinction. The Attach Request is a NAS message. The S1AP Initial UE Message is the transport mechanism used between the eNodeB and MME to deliver the NAS message.

One message can belong to one signaling layer while being transported through another. Understanding that distinction is essential for packet analysis.

Authentication: Establishing Trust

After receiving the attach request, the MME must determine whether the subscriber can be authenticated.

The MME may contact the HSS through the S6a interface using Diameter. The HSS provides authentication-related information that allows the network to challenge the UE.

UE MME HSS | | | | |-- Authentication --> | | | Information | | |<-- Authentication ---| | | Vectors | | | | |<-- Authentication Request ---------------| | | | |-- Authentication Response -------------->| | | |

The exact authentication exchange contains several cryptographic values and identities, but the engineering principle is more important than memorizing every field.

The network must prove that the UE possesses the credentials associated with the subscriber identity being used.

Successful authentication is followed by security procedures that establish protected signaling between the UE and the network.

Before the network allows a subscriber to establish meaningful service, it must establish who the subscriber is and whether that identity can be trusted.

Security Mode: Protecting the Signaling Relationship

Authentication establishes trust, but the signaling relationship also needs protection.

The MME can initiate a Security Mode Command, allowing the UE and network to activate the negotiated NAS security algorithms.

The UE responds with a Security Mode Complete.

MME UE | | |-- Security Mode Command ---------->| | | |<-- Security Mode Complete ---------| | |

From this point onward, protected NAS signaling becomes part of the subscriber's control-plane relationship with the MME.

This illustrates a broader telecom principle: security is not an optional layer added after connectivity. It is integrated into the process that creates connectivity.

Location and Mobility Context

The MME also needs to understand where the UE is operating within the LTE network.

LTE divides geographical coverage into Tracking Areas. The UE maintains tracking-area-related information so the network can determine where the subscriber can be reached without requiring continuous precise location updates.

This becomes especially important when the UE moves while remaining idle.

The network does not need to know the exact cell of every idle UE at every moment. Instead, it can maintain a coarser mobility context based on tracking areas.

Mobility management is a balance between knowing where the subscriber is and avoiding unnecessary signaling.

Creating the Default Bearer

After authentication and security procedures, the network establishes the packet-data session.

The concept of the default EPS bearer is central here.

The default bearer provides the initial logical path for IP connectivity between the UE and the PDN.

The MME coordinates with the SGW using S11, while the SGW and PGW establish the corresponding packet-data context through the EPC.

MME SGW PGW | | | |-- Create Session ->| | | |-- Create Session ->| | | | | |<-- Session Response| |<-- Session Response| | | | |

These are GTP-C signaling procedures.

The messages create the control-plane state required for the user-plane tunnel.

The PGW can allocate or associate an IP address with the subscriber's PDN session. The SGW maintains the corresponding tunnel context. The eNodeB receives the information required to establish the radio-side bearer and forwarding relationship.

The bearer is not just a tunnel. It is a contract between multiple network elements describing how a subscriber's traffic should be handled.

From Bearer Establishment to Real IP Traffic

Once the default bearer is established, the subscriber finally has a usable path for packet traffic.

UE | | Radio bearer v eNodeB | | S1-U / GTP-U v SGW | | S5/S8 / GTP-U v PGW | | IP v External Network

An application packet generated by the UE can now travel through this path.

The subscriber's original IP packet is encapsulated in GTP-U as it crosses the mobile core. The outer transport addresses identify the next tunnel endpoint, while the TEID identifies the logical tunnel context.

The control plane created the conditions under which this user-plane traffic can flow.

The first packet on the user plane is the consequence of many successful control-plane decisions.

Default Bearer and Dedicated Bearer

LTE supports more than one bearer concept because not all traffic needs to receive identical treatment.

The default bearer is established as part of the initial PDN connectivity. It provides baseline IP connectivity for the subscriber.

A dedicated bearer can later be established to provide specific QoS treatment for a particular service or traffic flow.

This becomes particularly relevant for services such as voice over LTE.

Subscriber PDN Session ``` PGW | +-------+-------+ | | Default Bearer Dedicated Bearer | | General traffic Specific service | | +-------+-------+ | UE ```

The dedicated bearer does not replace the default bearer. It exists alongside it.

This distinction is fundamental when analyzing QoS-related behavior.

Different services can share the same subscriber session while receiving different treatment from the network.

Service Request: Waking the User Plane

The LTE network is designed to conserve radio and network resources. A UE does not need to maintain an active radio connection continuously simply because it has an existing packet-data session.

When the UE has data to send or receive while in an idle state, it can trigger a Service Request.

The purpose of the Service Request procedure is to transition the UE into a state where user-plane resources can be re-established.

UE eNodeB MME | | | |-- Service Request->| | | |-- Service Request->| | | | | |<-- Context Setup --| |<-- Radio Resources-| | | | | |================ User Plane Restored ================|

The core session may still exist while the radio-side resources are temporarily released.

This distinction explains an otherwise confusing behavior: a subscriber can have an established IP session without continuously transmitting user-plane traffic over an active radio bearer.

Idle does not mean disconnected. It means the network has deliberately released resources while preserving enough state to resume service.

Tracking Area Update

As a UE moves through the network, its mobility context may need to be updated.

A Tracking Area Update (TAU) allows the network to update the UE's tracking-area information.

The procedure becomes particularly relevant when the UE moves into an area outside its current registered tracking area list.

UE eNodeB MME | | | |-- Tracking Area Update -> | | | |-- TAU Request ------>| | | | | |<-- TAU Accept -------| |<-- TAU Accept ------------| | | | |

The exact flow can involve additional procedures depending on the mobility scenario, including security, context transfer, and interactions with other MMEs.

The important idea is that mobility creates signaling even when the subscriber is not actively using an application.

A mobile network must manage movement even when there is no user traffic to manage.

Handover: When Mobility Becomes a Live Traffic Problem

Tracking Area Update should not be confused with handover.

A handover is concerned with moving an active radio connection from one cell or eNodeB to another while maintaining service continuity.

The exact procedure depends on the handover type and network architecture, but the fundamental challenge remains the same:

How do we move the radio connection without destroying the user's active session?

The network must coordinate radio resources, forwarding paths, tunnel endpoints, and subscriber context.

Mobility becomes difficult when the network must move a live session without letting the application notice that the path changed.

Detach: Ending the Relationship

Eventually, the UE may leave the network, power off, switch connectivity, or explicitly request detachment.

The Detach Procedure releases the relevant subscriber context.

UE eNodeB MME | | | |------ Detach Request ---->| | | |------ Detach ------->| | | | | | | | |<----- Release -------| |<------- Release ----------| |

The MME coordinates the necessary cleanup of the subscriber's control-plane state. The EPC can release bearer and session resources according to the detach scenario.

The network is therefore not only responsible for creating state. It must also know how to remove it safely.

Every session has a beginning, a maintained state, and an ending. A network that creates state well but releases it badly will eventually exhaust itself.

Understanding GTP Signaling in the Call Flow

GTP-C deserves special attention because it connects the mobility-control world with the packet gateway world.

During session establishment, GTP-C procedures communicate information about the subscriber's session and bearer context.

The MME can instruct the SGW to create or modify session state. The SGW can communicate with the PGW to create or modify the corresponding PDN connectivity.

The resulting state allows GTP-U tunnels to carry subscriber traffic.

Control Plane: MME | | GTP-C v SGW | | GTP-C v PGW User Plane: eNodeB | | GTP-U v SGW | | GTP-U v PGW

This separation is one of the most important things to recognize in a packet capture.

A GTP-C failure may prevent a bearer from being established. A GTP-U failure may cause an established bearer to carry no useful traffic.

GTP-C creates the road. GTP-U carries the vehicles.

Reading an Attach Failure

A practical engineer should be able to look at an incomplete attach and determine where the procedure stopped.

Consider several examples.

The UE never reaches the MME

If the UE sends an access request but the MME never receives the corresponding signaling, the investigation should focus on the radio side, eNodeB behavior, S1AP connectivity, or transport connectivity toward the MME.

The MME receives the request but authentication fails

Now the problem is likely farther into the control plane. S6a connectivity, Diameter exchanges, subscriber data, authentication vectors, identities, or security procedures become relevant.

Authentication succeeds but the bearer is not created

The investigation should move toward session management and GTP-C. The MME, SGW, PGW, APN configuration, and policy interactions become important.

The bearer exists but there is no user traffic

Now the user plane becomes the primary suspect. S1-U, S5/S8, TEIDs, GTP-U forwarding, routing, MTU, firewall policies, and external connectivity should be investigated.

The location of the failure in the call flow dramatically reduces the number of places you need to investigate.

From Signaling to Packet Capture

Call flows become particularly powerful when combined with packet analysis.

Suppose a capture shows:

S1AP | +-- Initial UE Message | +-- Downlink NAS Transport | +-- Uplink NAS Transport | +-- Initial Context Setup | +-- UE Context Release

The engineer should immediately ask:

  • Which NAS messages were transported?
  • Did authentication succeed?
  • Was security activated?
  • Was the default bearer established?
  • Did GTP-C create the session?
  • Were GTP-U packets observed afterward?
  • Were the expected TEIDs present?
  • Did the eNodeB receive the correct user-plane parameters?

This transforms packet capture analysis from packet-by-packet inspection into reconstruction of network behavior.

The best packet capture analysis is not about finding a strange packet. It is about finding the first event that breaks the expected sequence.

VoLTE and IMS: Extending LTE Beyond Data

LTE was designed primarily as a packet-based mobile architecture. Traditional circuit-switched voice was not simply carried through the EPC in the same way as legacy 2G or 3G voice.

To provide voice services over LTE, operators adopted IMS — IP Multimedia Subsystem.

VoLTE therefore adds another signaling ecosystem on top of the LTE packet-data architecture.

LTE / EPC UE | | LTE-Uu v eNodeB | | S1 v EPC | | IP Connectivity v IMS | +---- P-CSCF | +---- I-CSCF | +---- S-CSCF | +---- Application / Service Functions

At a high level, LTE provides the IP connectivity while IMS provides the service architecture required for IP-based voice and multimedia services.

SIP becomes a central signaling protocol for IMS.

A VoLTE call therefore involves multiple layers of signaling:

  • LTE access and mobility procedures
  • EPS bearer establishment
  • IMS registration
  • SIP signaling
  • Dedicated QoS treatment for voice media
  • RTP media transport

This is why troubleshooting VoLTE requires engineers to understand both the mobile packet core and the IMS service layer.

The IMS Registration Concept

Before the UE can normally use IMS services, it must establish connectivity to the IMS domain and register its identity.

The UE obtains IP connectivity through the LTE packet core and then communicates with the IMS infrastructure using SIP.

UE EPC IMS | | | |-- IP Connectivity>| | | | | |----------------------------------------->| | SIP REGISTER | | | | |<-----------------------------------------| | SIP Response | | | | |=========== IMS Registration Complete ===|

The exact IMS registration process involves authentication and multiple SIP messages, but the architectural lesson is straightforward:

LTE provides the packet transport. IMS provides the service logic.

VoLTE is not “voice inside LTE” as a single protocol. It is an IP service built on top of a mobile packet architecture.

Dedicated Bearers and Voice QoS

Voice traffic has requirements that differ from ordinary best-effort Internet traffic. Latency, jitter, packet loss, and predictable treatment matter significantly.

The LTE architecture can establish dedicated bearers associated with specific service flows.

Default Bearer | +---- General IP connectivity | | +---- Dedicated Bearer | +---- Voice service | +---- Specific QoS treatment

This allows the network to distinguish voice traffic from ordinary data traffic.

The precise QoS parameters depend on the service and operator implementation, but the engineering principle is universal:

When every packet is treated equally, real-time services eventually reveal the limits of best-effort networking.

Following a VoLTE Call

A simplified VoLTE call can be viewed as several nested procedures.

MOBILE ACCESS UE | | LTE signaling v eNodeB | | EPC signaling v MME / SGW / PGW | | IP connectivity v IMS | | SIP v Call Control | | RTP v Voice Media

The call therefore has both a signaling path and a media path.

SIP signaling establishes and controls the call. RTP carries the actual voice media. LTE/EPC provides the underlying IP transport and QoS mechanisms.

For voice troubleshooting, ask two separate questions: “Can the call be established?” and “Can the media flow correctly?”

A call can successfully establish while one-way audio or no-audio problems remain. That immediately suggests that SIP signaling and RTP media must be investigated separately.

The Engineer's Call Flow Method

When approaching any LTE signaling problem, a useful method is to reconstruct the expected sequence.

Start with the subscriber.

Ask what state the UE should be in.

Identify the next expected signaling message.

Identify the node responsible for generating it.

Identify the interface and protocol that should carry it.

Then determine whether the message was actually observed.

Expected event | v Expected node | v Expected interface | v Expected protocol | v Message observed? / \ YES NO | | | +---- Investigate previous boundary | v What state changed? | v What should happen next?

This methodology works because telecom signaling is deterministic enough to establish an expected sequence while still being complex enough that failures can occur at many different points.

Troubleshooting is often the search for the first missing message.

The Bigger Picture

The attach procedure, authentication, bearer establishment, Service Request, Tracking Area Update, Detach, and VoLTE signaling may initially look like unrelated procedures.

They are not.

They are different manifestations of the same underlying principle: the mobile network continuously creates, modifies, and removes distributed subscriber state.

The UE moves. The network authenticates it. The MME tracks it. The EPC creates tunnels for it. The policy system determines how its traffic should be treated. The radio network allocates resources. IMS can establish services on top of the resulting IP connectivity.

Every action changes the state of multiple components.

A mobile network is alive in its signaling. User traffic is only the visible consequence.

Chapter Takeaways

The LTE signaling architecture becomes much easier to understand once every procedure is viewed as a state transition.

The Attach Procedure establishes the subscriber's initial relationship with the LTE core.

Authentication establishes trust between the subscriber and the network.

Security Mode activates protected NAS signaling.

The Default Bearer establishes baseline packet-data connectivity.

A Dedicated Bearer can provide specialized treatment for particular services.

The Service Request allows a UE with an existing session to restore active resources when needed.

The Tracking Area Update maintains the UE's mobility context.

The Detach Procedure releases subscriber state and network resources.

NAS carries mobility and session-related signaling between the UE and core. S1AP provides the eNodeB-to-MME signaling framework. SCTP transports S1AP. GTP-C creates and manages EPC session and bearer state. GTP-U transports subscriber traffic.

And with IMS, LTE becomes more than a packet-data access network. It becomes the foundation for IP-based communication services such as VoLTE.

SIGNALING MENTAL MODEL ``` UE State | v Radio Connectivity | v NAS Signaling | v Authentication | v Security Context | v Session Creation | v Default Bearer | v User Plane | v Mobility / Service | v Dedicated Services / IMS | v Release ```

Once this sequence becomes intuitive, LTE traces stop looking like random messages. They become a conversation with a predictable structure.

Do not memorize the call flow. Learn to predict the next message.

That is the point at which signaling knowledge becomes engineering knowledge.

In the next chapter, we will take this understanding into the most practical part of LTE engineering: troubleshooting the EPC and user plane. We will move from expected behavior to failed behavior and learn how to determine where packets, tunnels, bearers, and sessions stop working.

The architecture shows where the problem can be. The call flow shows when the problem begins.

Chapter 9: NFVI, Virtualization and Cloud-Native Networking

The infrastructure beneath the mobile core.

A telecom network may look like software from the outside. Underneath that software, packets still have to move through real CPUs, memory, buses, interfaces, and clocks.

The previous chapters focused on the behavior of the mobile core.

We followed signaling through the EPC. We followed registration and PDU Session Establishment through the 5G Core. We analyzed PFCP, GTP-U, QoS, and call flows.

But there is another layer beneath all of this.

The AMF needs CPU. The SMF needs memory. The UPF needs extremely fast packet processing. The databases need storage and network connectivity. The signaling interfaces need predictable latency.

The network functions may be implemented as software, but software still requires infrastructure.

When a telecom network becomes software, the infrastructure becomes part of the network.

From Hardware Appliances to Software

Traditional telecom networks were heavily dependent on dedicated hardware appliances.

A network element could arrive as a physical system containing:

  • CPU resources
  • Memory
  • Network interfaces
  • Specialized packet-processing hardware
  • Operating software

The hardware and software were frequently designed as one product.

Network Function Virtualization changed that model.

Traditional Model +-----------------------------+ | Dedicated Telecom Appliance | | | | CPU | | Memory | | NIC | | Network Function | +-----------------------------+ Virtualized Model +-----------------------------+ | Commodity Server | | | | Hypervisor | | | | | +---- VM | | | | | Network Function| +-----------------------------+

The objective was to decouple the network function from the physical appliance.

That introduced flexibility.

But it also introduced new engineering problems.

Virtualization removes hardware dependency. It does not remove hardware behavior.

NFV

Network Function Virtualization, or NFV, is the approach of implementing network functions as software workloads running on virtualized infrastructure.

Instead of requiring a dedicated physical appliance for every function, a telecom operator can deploy software on standardized compute infrastructure.

Physical Infrastructure | v Virtualization Layer | v Virtual Machines | v Virtual Network Functions | v Telecom Services

A virtual EPC, for example, can be distributed across multiple virtual machines.

NFVI ``` +---------------------+ | Compute | | Storage | | Networking | +----------+----------+ | Hypervisor | +-----------+-----------+ | | | VM VM VM | | | MME SGW PGW ```

This architecture provides significant operational flexibility.

Resources can be allocated dynamically. Virtual machines can be instantiated from templates. Capacity can be increased without deploying an entirely new appliance.

But telecom workloads have requirements that ordinary enterprise applications often do not.

A web server can tolerate occasional latency spikes. A packet-processing workload may not have the same luxury.

NFVI

The infrastructure supporting these virtualized network functions is commonly referred to as NFVI — Network Functions Virtualization Infrastructure.

A simplified view is:

NFVI +---------------------------------------+ | Physical Infrastructure | | | | Compute Memory NICs Storage | +---------------------------------------+ | +---------------------------------------+ | Virtualization / Infrastructure Layer | +---------------------------------------+ | +---------------------------------------+ | Virtual Machines / Containers | +---------------------------------------+ | +---------------------------------------+ | Network Functions | +---------------------------------------+

NFVI therefore includes much more than servers.

It includes:

  • Compute resources
  • Memory
  • Network interfaces
  • Virtual switches
  • Storage
  • Hypervisors
  • Accelerators
  • High-speed networking
  • Time synchronization infrastructure

A performance problem at any of these layers can become a telecom problem.

Virtual Machines

A virtual machine provides an isolated operating-system environment running on a hypervisor.

Physical Server | v Hypervisor | +-----+-----+-----+ | | | | VM1 VM2 VM3 VM4 | | | | OS OS OS OS | | | | NF NF NF NF

Each VM has virtual CPU, memory, storage, and network interfaces.

The hypervisor maps those virtual resources to physical resources.

This abstraction is powerful.

It is also where overhead can appear.

A packet entering a VM does not necessarily travel directly from the physical NIC to the application.

Physical NIC | v Host | v Virtual Switch | v Virtual NIC | v Guest OS | v Application

Every additional processing layer can introduce CPU consumption and latency.

Containers

Containers use a different model.

Instead of virtualizing a complete operating system for every workload, containers share the host kernel while isolating application processes.

Physical Server | v Host Linux Kernel | +-----+-----+-----+ | | | | C1 C2 C3 C4 | | | | NF NF NF NF

This makes containers lightweight compared with traditional virtual machines.

They can start quickly and consume fewer resources for the virtualization boundary itself.

This model became particularly important with cloud-native telecom architectures.

Virtual machines changed where network functions could run. Containers changed how quickly and how dynamically they could be deployed.

VMs Versus Containers

VM Container Isolation Strong Process-level Kernel Separate Shared Startup Usually slower Usually faster Footprint Larger Smaller Density Lower Higher Lifecycle VM-oriented Application-oriented Cloud-native Possible Native model

This does not mean containers are automatically faster.

A container can still consume enormous CPU resources.

A poorly designed containerized UPF can still experience packet loss.

The abstraction layer changes, but physics remains.

Containers remove some virtualization overhead. They do not eliminate CPU contention, memory latency, packet processing cost, or network bottlenecks.

Virtual Networking

Networking becomes considerably more interesting once the network function is no longer directly attached to a physical interface.

Physical NIC | v Host Kernel | v Virtual Switch | +--------+ | | v v VM1 VM2 | | vNIC vNIC | | NF NF

The virtual switch becomes part of the packet path.

Depending on the platform, packets may traverse kernel networking, virtual switching, bridging, overlays, security processing, and other components.

For ordinary enterprise workloads this may be acceptable.

For a high-throughput UPF handling massive packet rates, it can become a serious engineering consideration.

The Packet Path Matters

Consider two possible paths.

PATH A — Conventional NIC | v Kernel | v Virtual Switch | v vNIC | v Application
PATH B — Accelerated NIC | v Direct / Accelerated Path | v Application

The second path can reduce the amount of software processing required per packet.

That can be extremely valuable in telecom workloads.

At high packet rates, saving a small amount of CPU work per packet can become a massive system-level gain.

SR-IOV

Single Root I/O Virtualization, or SR-IOV, allows a physical PCIe device to expose multiple virtual functions.

Physical NIC | Physical Function | +------------+------------+ | | | VF0 VF1 VF2 | | | VM1 VM2 VM3

Instead of forcing every virtual workload to communicate through a traditional virtual switch path, a virtual function can provide a more direct interface to a workload.

This can reduce overhead and improve packet-processing performance.

The trade-off is complexity.

SR-IOV requires coordination between:

  • BIOS
  • CPU / PCIe topology
  • NIC
  • Host operating system
  • Hypervisor
  • Virtual machine or container platform
  • Network function
Performance acceleration is never just a checkbox. It is a chain of dependencies.

DPDK

Data Plane Development Kit, or DPDK, is a collection of libraries and drivers designed to accelerate packet processing in user space.

Traditional Linux networking involves the kernel network stack.

NIC | v Linux Kernel | v Network Stack | v Socket | v Application

DPDK can provide a different processing model.

NIC | v DPDK | v User-space Packet Processing | v Network Application

The objective is to process packets with much lower overhead and higher efficiency.

This can involve techniques such as:

  • Polling instead of relying entirely on interrupts
  • Large batches of packets
  • Efficient memory access
  • User-space drivers
  • Pre-allocated packet buffers
  • Reduced kernel transitions

The trade-off is CPU consumption.

A polling-based packet-processing application may intentionally keep CPU cores busy.

In high-performance telecom networking, a CPU core showing 100% utilization is not automatically a problem. It may be doing exactly what it was designed to do.

Interrupts Versus Polling

Traditional network applications often depend heavily on interrupts.

Packet Arrives | v NIC Interrupt | v CPU Wakes / Handles Event | v Process Packet

At very high packet rates, interrupt handling itself can become expensive.

A polling architecture takes a different approach.

CPU Core | +---- Poll NIC | +---- Check Packet | +---- Process Packet | +---- Poll Again | +---- Poll Again | +---- Poll Again

The CPU is continuously available for packet processing.

This can improve predictability and throughput.

But it consumes dedicated CPU resources.

Hugepages

Memory management becomes increasingly important when packet-processing performance matters.

Traditional memory pages are relatively small.

Large memory pages, commonly called hugepages, reduce the number of page-table entries required to map large amounts of memory.

Normal Pages Memory |*|*|*|*|*|*|*|*|*|*|*|*|*|*|*|*| Hugepages |*******|*******|*******|*******|

Fewer page mappings can reduce translation overhead.

Hugepages are especially relevant for workloads using DPDK and other high-performance networking frameworks.

They can also provide more predictable memory behavior when correctly configured.

Hugepages are not a magic performance switch. They are one component of a larger memory and CPU architecture.

CPU Pinning

A telecom workload should not necessarily be allowed to move freely across every CPU core.

CPU pinning assigns a workload to specific CPU cores.

Physical CPU Core 0 -> OS Core 1 -> OS Core 2 -> UPF worker Core 3 -> UPF worker Core 4 -> UPF worker Core 5 -> UPF worker Core 6 -> Other workload Core 7 -> Other workload

Why does this matter?

Because CPU migration has costs.

Cache locality can change. Scheduling decisions can change. A workload can compete with unrelated processes.

For latency-sensitive packet processing, these effects can become visible.

Predictable performance often requires predictable CPU placement.

CPU Isolation

CPU pinning is closely related to CPU isolation.

The objective is to prevent unrelated operating-system activities from interfering with critical packet-processing cores.

CPU 0 OS / System CPU 1 OS / System CPU 2 Dedicated to UPF CPU 3 Dedicated to UPF CPU 4 Dedicated to UPF CPU 5 Dedicated to UPF

The goal is not necessarily maximum CPU utilization.

The goal is predictable execution.

Telecom performance is often about controlling variability, not simply maximizing average throughput.

NUMA Awareness

Modern servers often contain multiple CPU sockets or NUMA nodes.

NUMA stands for Non-Uniform Memory Access.

NUMA NODE 0 NUMA NODE 1 ``` +-------------+ +-------------+ | CPU | | CPU | | CPU | | CPU | | CPU | | CPU | +------+------+\ +------+------+ | | v v Memory 0 Memory 1 \____________________________/ Interconnect ```

A CPU can access memory associated with its local NUMA node more efficiently than memory attached to another node.

This becomes critical for high-performance packet processing.

Imagine a NIC physically connected to NUMA node 0.

NIC | v PCIe | v NUMA Node 0 | +---- CPU 0 | +---- Memory 0 Bad placement: NIC | v NUMA 0 | Interconnect | v NUMA 1 | CPU

The second configuration may introduce additional latency and memory-access overhead.

If the NIC, CPU, and memory are on different NUMA nodes, the packet may cross the architecture before the application even sees it.

NUMA-Aware Design

A high-performance network function should ideally align:

NIC | v PCIe | v NUMA Node | +---- CPU Cores | +---- Memory | +---- Packet Processing

This is why telecom deployment specifications often include explicit CPU and NUMA requirements.

A server can have enormous CPU capacity and still perform poorly if the workload is placed incorrectly.

PTP and Time Synchronization

Performance is not the only infrastructure requirement.

Telecom networks also depend heavily on accurate time.

Precision Time Protocol, or PTP, is used to synchronize clocks across networked systems with very high precision.

Grandmaster Clock | +---------+---------+ | | | v v v gNB UPF Other NF | | | +---------+---------+ | Synchronized Time

Time synchronization is particularly important in radio networks and distributed telecom infrastructure.

The engineering challenge is not simply synchronizing the operating-system clock.

Hardware timestamping, NIC capabilities, network topology, boundary clocks, transparent clocks, and PTP configuration can all matter.

A distributed telecom system cannot behave like one system if its components do not agree on time.

Why Time Matters to Telecom

Consider a radio network with tightly coordinated transmission behavior.

Small timing errors can affect:

  • Radio synchronization
  • Frame alignment
  • Frequency coordination
  • Interference management
  • Distributed radio functions

This becomes increasingly important as network architectures become more distributed.

PTP is infrastructure, but its consequences are visible at the radio and service level.

The Performance Stack

A telecom packet does not experience performance at just one layer.

Application | Network Function | Packet Processing Framework | Container / VM | Virtual Networking | Host Kernel / Hypervisor | NIC | PCIe | NUMA | CPU / Memory | Physical Network

Every layer can contribute to latency, throughput limitations, jitter, or packet loss.

When performance is bad, the question is not “Is the application slow?” The question is “Which layer is adding the cost?”

Throughput Is Not Enough

A common mistake is to evaluate telecom infrastructure only by throughput.

Suppose a UPF can process:

100 Gbit/s average throughput

That number sounds excellent.

But what if the workload experiences significant latency spikes under packet-per-second load?

What if packets are dropped when packet size becomes small?

What if one CPU core becomes saturated while the remaining cores are idle?

What if packet processing becomes unpredictable during peak traffic?

Average throughput does not answer these questions.

Telecom performance must consider:

  • Throughput
  • Packets per second
  • Latency
  • Jitter
  • Packet loss
  • CPU utilization
  • Memory bandwidth
  • Cache behavior
  • NUMA locality
  • Interrupt behavior
  • Queue depth

Packets Per Second

Bandwidth alone can be misleading.

A network processing large packets and a network processing tiny packets may have the same bitrate but radically different CPU requirements.

Large packets: Few packets | v Less per-packet processing Small packets: Many packets | v More per-packet processing | v Higher CPU pressure

This is why packets per second can become a critical metric for user-plane workloads.

Bits measure how much traffic exists. Packets determine how much work the CPU must perform.

Latency and Jitter

Latency measures how long a packet takes to traverse a system.

Jitter describes variation in that delay.

Packet 1 ---- 20 μs Packet 2 ---- 21 μs Packet 3 ---- 20 μs Packet 4 ---- 22 μs Packet 5 ---- 80 μs

The average might still look acceptable.

But the outlier matters.

For latency-sensitive telecom workloads, tail latency can be more important than average latency.

A network that is fast most of the time but unpredictable under load can be harder to operate than a network that is consistently slightly slower.

Queueing and Buffering

Packets do not always move immediately from one component to another.

They may wait in queues.

NIC | v RX Queue | v Packet Processing | v TX Queue | v NIC

If processing cannot keep up with packet arrival, queues grow.

Eventually buffers may fill and packets can be dropped.

This creates an important troubleshooting pattern:

Traffic increases | v CPU pressure increases | v Queues grow | v Latency increases | v Buffers fill | v Packet loss

The final symptom may be packet loss.

But the root cause may be CPU contention several layers below.

Cloud-Native Networking

As telecom networks evolved toward cloud-native architectures, the infrastructure model changed again.

Physical Infrastructure | v Cloud Platform | v Kubernetes | v Container Network | v CNF | v Telecom Service

This introduces additional abstractions.

Containers need networking.

Networking requires interfaces.

Interfaces require connectivity to the physical infrastructure.

High-performance telecom applications may therefore require mechanisms such as SR-IOV, specialized CNI configurations, CPU pinning, hugepages, and NUMA-aware placement.

These topics become especially important for cloud-native network functions.

The Cloud-Native Performance Problem

Cloud-native architecture provides tremendous flexibility.

But flexibility can conflict with deterministic performance if the infrastructure is not carefully designed.

Highly Flexible Container | Scheduler | Any CPU | Any NUMA | Any Node | Virtual Network

This is convenient for generic workloads.

For a high-performance UPF, however, the desired architecture may look very different.

UPF Container | Dedicated CPU | Specific NUMA Node | Local Memory | SR-IOV VF | High-Speed NIC
Cloud-native does not mean “ignore the hardware.” In telecom, cloud-native often means learning how to control the hardware through software.

Troubleshooting Performance

When a telecom application reports poor performance, do not start by restarting it.

Build a performance path.

Application | v CPU | v Memory | v NUMA | v Virtual Interface | v Virtual Switch / SR-IOV | v Physical NIC | v Network

Then ask questions at every layer.

  • Is the application CPU-bound?
  • Are packet-processing cores saturated?
  • Are workloads migrating between CPUs?
  • Is the workload crossing NUMA nodes?
  • Are hugepages correctly allocated?
  • Is SR-IOV configured?
  • Is DPDK using the expected interface?
  • Are RX/TX queues correctly configured?
  • Are packets being dropped at the NIC?
  • Is the virtual switch becoming a bottleneck?
  • Is memory bandwidth saturated?
Performance troubleshooting is architecture troubleshooting with numbers attached.

A Practical Example: UPF Packet Loss

Imagine a UPF starts dropping packets during peak traffic.

The first instinct might be:

“The UPF software is broken.”

But consider the actual chain.

Traffic Increase | v Packet Rate Increase | v CPU Core Saturation | v RX Queue Growth | v Buffer Exhaustion | v Packet Loss

Now imagine the CPU itself is not fully saturated.

Perhaps the NIC is attached to NUMA node 0 while the packet-processing cores are running on NUMA node 1.

NIC | v NUMA 0 | | Interconnect v NUMA 1 | v CPU | v UPF

The performance problem may be architectural rather than application-level.

Move the CPU and memory closer to the NIC.

The same software may suddenly process more packets with lower latency.

Sometimes the fastest way to optimize software is to move it closer to the hardware it already depends on.

A Practical Example: High CPU Usage

Suppose monitoring reports:

UPF CPU = 95% Traffic = Moderate Packet Loss = 0% Latency = Stable

Is this a problem?

Not necessarily.

If the workload is deliberately using dedicated polling cores, high utilization may be expected.

Now compare:

UPF CPU = 95% Traffic = Moderate Packet Loss = Increasing Latency = Increasing

Now the interpretation changes.

The same CPU metric has a different meaning because the surrounding evidence changed.

A metric is not a diagnosis. A metric becomes useful when correlated with behavior.

Performance Baselines

A production network should have a known baseline.

Engineers should know what normal looks like.

Normal Load | +---- CPU +---- PPS +---- Throughput +---- Latency +---- Jitter +---- Packet Loss +---- Queue Depth +---- Memory +---- NIC Counters

Without a baseline, every incident becomes a guessing exercise.

With a baseline, deviations become evidence.

You cannot reliably troubleshoot abnormal behavior if you never measured normal behavior.

Observability Across the Stack

Cloud-native telecom environments require visibility across multiple layers.

Application Metrics | Container Metrics | Kubernetes Metrics | Host Metrics | NIC Metrics | Network Metrics | Physical Infrastructure

A single dashboard rarely tells the whole story.

The engineer needs correlation.

For example:

13:00 Traffic +30% CPU +25% PPS +40% RX Drops +5% Latency +20%

Those values together tell a story.

A single CPU graph would not.

The Hidden Cost of Abstraction

Virtualization and cloud-native technologies introduce abstraction layers.

Each layer provides operational advantages.

Each layer can also hide what is actually happening.

Application | Container | Pod | CNI | Virtual Interface | Virtual Switch | Host | NIC | PCIe | NUMA | CPU

An application engineer may only see:

“Packets are slow.”

A telecom infrastructure engineer sees a much larger system.

That is the difference between application troubleshooting and infrastructure-aware troubleshooting.

The more abstract the platform becomes, the more important it is to understand what the abstraction is hiding.

The Telecom Engineer's New Skill Set

The modern telecom engineer cannot remain isolated inside the protocol stack.

Understanding GTP-U is essential.

But understanding how GTP-U is processed by a CPU is also essential.

Understanding PFCP is essential.

But understanding how the UPF receives the resulting packets is equally important.

Understanding a 5G architecture diagram is only one part of the job.

Telecom Protocols + Linux + Virtualization + Networking + Containers + Kubernetes + Hardware + Observability = Modern Telecom Engineering
The modern telecom engineer operates at the boundary between telecommunications and computing.

What Changes from EPC to 5G Cloud-Native Networks?

The transition from EPC to 5G Core is not simply a change in network functions.

The operational model also changes.

Legacy Telecom Hardware Appliance | Network Function | Service Modern Telecom Commodity Hardware | Virtualization | Cloud Platform | Container / CNF | Network Function | Service

This creates greater flexibility, but also requires engineers to understand more layers.

A failure can originate in the application.

It can originate in the container.

It can originate in Kubernetes.

It can originate in the CNI.

It can originate in the host.

It can originate in the NIC.

Or it can originate in the physical network.

Modern telecom troubleshooting is increasingly a distributed-systems problem with packets at its center.

The Complete Performance Picture

A high-performance telecom platform can be understood as a chain.

APPLICATION | v NETWORK FUNCTION | v PACKET PROCESSING | v CPU / MEMORY | v NUMA | v PCIe / NIC | v VIRTUAL NETWORK | v PHYSICAL NETWORK

A weakness at any point can affect the service.

That is why telecom performance engineering is fundamentally a systems discipline.

It is not enough to optimize one component.

The entire path must work together.

Chapter Takeaways

NFV introduced the idea that telecom network functions could be implemented as software running on standardized infrastructure.

NFVI provides the compute, memory, storage, networking, virtualization, and supporting infrastructure required by those workloads.

Virtual machines provide strong workload isolation but introduce virtualization overhead.

Containers provide a lighter application-oriented model and became fundamental to cloud-native telecom architectures.

Virtual networking can introduce additional packet-processing layers.

SR-IOV can provide more direct access to high-performance network interfaces.

DPDK can accelerate packet processing by moving critical operations into efficient user-space processing paths.

Hugepages improve memory-management efficiency for suitable high-performance workloads.

CPU pinning provides predictable processor placement.

NUMA awareness keeps CPUs, memory, and network interfaces physically close within the server architecture.

PTP provides the accurate time synchronization required by many telecom systems.

And performance must be evaluated using more than throughput.

Performance Throughput + Packets / Second + Latency + Jitter + Packet Loss + CPU + Memory + NUMA + NIC + Queues + Time Synchronization

The most important lesson is simple:

A 5G Core may be implemented in software, but its performance is still constrained by real hardware, real memory, real networks, and real time.

Once these concepts are understood, cloud-native telecom infrastructure becomes much easier to reason about.

The next step is to move deeper into the platform that orchestrates these workloads.

That means Kubernetes, containers, CNFs, CNI, Multus, service networking, scheduling, high-performance interfaces, and the operational model required to run telecom workloads at scale.

The network has become software. The engineer's responsibility has therefore expanded from understanding packets to understanding the platform that moves them.

Chapter 11: Mobile Network Security

Protecting the signaling, control, user plane, infrastructure, and trust relationships that make a mobile network operate.

A mobile network is not secure because it has a firewall. It is secure when every trust relationship has been understood, controlled, monitored, and continuously challenged.

Mobile networks are among the most complex communication systems ever deployed at scale.

They connect millions of subscribers.

They exchange signaling with other operators.

They interact with roaming partners.

They connect radio networks to packet cores.

They transport voice, messaging, internet traffic, enterprise services, IoT traffic, and increasingly cloud-native applications.

Every one of those capabilities introduces trust relationships.

And every trust relationship creates a security boundary.

The attack surface of a mobile network is not a single interface. It is the entire ecosystem of interfaces, protocols, identities, applications, and infrastructure that the network trusts.

Security Begins With Architecture

Security should not be added after the network has been deployed.

It must be considered when the architecture is designed.

INTERNET | v +-------------+ | Security | | Boundary | +------+------+ | v Mobile Core | +-----------------+-----------------+ | | | v v v Control User Plane Management Plane | Plane | | | +------------------+-----------------+ | v RAN / UE

Each of these planes has different requirements.

The management plane must be protected against unauthorized administrative access.

The control plane must protect signaling and session management.

The user plane must prevent unauthorized traffic, manipulation, and abuse.

The infrastructure itself must also be protected.

Trust Is the Real Security Boundary

One of the most dangerous assumptions in telecom security is:

“This is internal traffic, therefore it is trusted.”

Mobile networks contain many internal interfaces.

But internal does not automatically mean trustworthy.

A compromised network element can generate traffic that looks completely legitimate.

A compromised partner connection can introduce malicious signaling.

A vulnerable management interface can become an entry point into the core.

An IP address tells you where traffic came from. It does not tell you whether the traffic should be trusted.

The Legacy Signaling Environment

Mobile networks evolved over decades.

Older signaling technologies remain relevant because modern networks still interact with legacy systems.

Three protocols are particularly important when discussing telecom security:

  • SS7
  • Diameter
  • GTP

Each protocol operates in a different part of the mobile architecture.

Legacy / 2G / 3G | SS7 | v Signaling 4G EPC | Diameter | v Policy / Subscriber Functions 4G / 5G User Plane | GTP | v Packet Transport

Understanding the protocol is not enough.

The engineer must understand the trust model around the protocol.

SS7 Security

SS7 was designed in an environment where signaling networks were highly controlled.

The architecture assumed trusted participants.

The modern internet does not operate under those assumptions.

As telecom networks became increasingly interconnected, SS7 signaling became an attractive target.

Potential abuse can involve:

  • Location-related information exposure
  • Subscriber information queries
  • Fraud
  • Message manipulation
  • Unauthorized signaling procedures

The important lesson is not that SS7 is “old.”

The deeper lesson is that protocol trust assumptions can become security vulnerabilities when the environment changes.

A protocol can be technically correct and still be insecure when the assumptions surrounding its trust model are no longer valid.

Diameter Security

Diameter became a major signaling protocol in 4G networks.

It is heavily involved in subscriber authentication, policy, charging, and mobility-related functions.

EPC ``` +-------------+ | HSS | +------+------+ | Diameter | +------+------+ | MME | +-------------+ +-------------+ | PCRF | +------+------+ | Diameter | +------+------+ | PCEF | +-------------+ ```

Diameter introduces powerful capabilities.

It also creates important signaling dependencies.

A compromised or poorly protected Diameter peer can potentially generate malformed, unauthorized, or abusive signaling.

Therefore, security controls should consider:

  • Peer authentication
  • Network-level access control
  • Message validation
  • Topology awareness
  • Rate limiting
  • Monitoring
  • Anomaly detection

GTP Security

GTP is fundamental to packet mobility networks.

GTP-C controls sessions.

GTP-U transports user traffic.

Control Plane ``` GTP-C | v ``` Session Management ``` User Plane GTP-U | v User Traffic ```

The distinction is critical from a security perspective.

An attacker targeting GTP-C may attempt to manipulate session establishment or modification.

An attacker targeting GTP-U may attempt to inject, redirect, or otherwise abuse user-plane traffic.

Control-plane attacks manipulate the network's decisions. User-plane attacks manipulate what the network carries.

Signaling Attacks

Signaling is the nervous system of a mobile network.

It tells network elements:

  • Who the subscriber is
  • Where the subscriber is
  • Which session should exist
  • Which resources should be allocated
  • Which policies should apply
  • Where traffic should be forwarded

If signaling is abused, the attacker may not need to compromise the user-plane infrastructure.

Manipulating the decisions that control the network can be enough.

Attack ``` | v Signaling Layer | +---------+---------+ | | | v v v Identity Session Policy Context State Rules | | | +---------+---------+ | v Service Impact ```

Signaling Floods

One class of attack involves overwhelming signaling functions with excessive requests.

A network element may have plenty of CPU capacity for normal traffic.

But signaling traffic can trigger expensive operations.

Authentication.

Database lookups.

Session creation.

Policy evaluation.

State allocation.

Logging.

A relatively small amount of malicious traffic can therefore create disproportionate load.

The most dangerous packet is not always the packet that consumes the most bandwidth. Sometimes it is the packet that makes the network do the most work.

GTP Attacks

GTP deserves particular attention because it carries mobility-related control information and user-plane traffic.

Potential attack categories include:

  • Unauthorized GTP peers
  • Malformed signaling
  • Session manipulation
  • Tunnel abuse
  • Traffic injection
  • Source validation failures
  • Unexpected TEID behavior

Security controls should therefore understand the expected topology.

Expected gNB / eNodeB | v UPF / SGW | v Core Unexpected Unknown Source | v GTP | X BLOCK / ALERT

The important point is that GTP traffic should not be treated as trustworthy simply because it uses UDP and comes from an apparently internal network.

TEIDs and Security

TEIDs identify GTP tunnels.

From the troubleshooting perspective, they are essential for following a session.

From a security perspective, they are also valuable signals.

A security monitoring system can establish relationships between:

Subscriber | +---- Session | +---- GTP Tunnel | +---- TEID | +---- Source | +---- Destination

Unexpected combinations can become indicators of suspicious behavior.

The security engineer should therefore understand the same identifiers used by the network engineer during troubleshooting.

The identifiers that help you troubleshoot a network can also help you detect an attack.

4G Security Architecture

The 4G EPC introduced a more structured security architecture than previous generations.

4G EPC ``` +-----------------------+ | HSS | +-----------+-----------+ | | +-----------v-----------+ | MME | +-----------+-----------+ | Control Plane | +-----------v-----------+ | SGW / PGW | +-----------+-----------+ | User Plane | UE ```

Authentication, subscriber identity management, bearer establishment, and policy control are distributed across multiple functions.

This improves separation of responsibilities.

But it also increases the number of interfaces that must be secured and monitored.

5G Security Architecture

5G introduces another significant architectural change.

The core becomes increasingly cloud-native and service-oriented.

5G Core ``` +------+ +------+ +------+ | AMF | | SMF | | PCF | +--+---+ +--+---+ +--+---+ | | | +---------+---------+ | Service-Based Interfaces | +------------+------------+ | | UDM AUSF | | +------------+------------+ | NRF | v UPF ```

This creates new security considerations.

Instead of securing only traditional telecom signaling protocols, engineers must also protect:

  • HTTP/2 communication
  • REST-style APIs
  • Service discovery
  • Network Function identities
  • Cloud infrastructure
  • Container environments
  • Orchestration platforms
5G did not remove the telecom attack surface. It expanded it into the cloud-native and API world.

4G and 5G Security Differences

The transition from EPC to 5GC changes more than network function names.

4G EPC Network Functions | Traditional Interfaces | Diameter / GTP / SCTP | Virtualized Infrastructure 5G Core Network Functions | Service-Based Architecture | HTTP/2 / APIs | Cloud-Native Infrastructure | Containers / Kubernetes | Virtualized / Bare Metal

This creates a broader security domain.

A 5G security architecture must consider telecom protocols and cloud security simultaneously.

The security engineer increasingly needs knowledge of:

  • IP networking
  • Telecom signaling
  • HTTP/2
  • APIs
  • TLS
  • Containers
  • Kubernetes
  • Linux
  • Cloud infrastructure

Service-Based Interfaces

In 5G, network functions communicate through service-based interfaces.

This creates a model that looks familiar to cloud engineers.

AMF | | HTTP/2 v SMF | | HTTP/2 v UDM / PCF / NRF

The security implications are significant.

The API becomes part of the telecom attack surface.

An attacker may attempt to exploit:

  • Authentication weaknesses
  • Authorization weaknesses
  • Improper input validation
  • API abuse
  • Service discovery manipulation
  • Denial of service

This is where telecom security and application security increasingly converge.

Network Function Identity

In a service-based architecture, knowing which network function is communicating is fundamental.

The system must be able to distinguish legitimate network functions from unauthorized clients.

NRF ``` | Network Function Registration | +---------+---------+ | | | v v v AMF SMF PCF | | | +---------+---------+ | Service Access ```

Identity therefore becomes a security control.

Discovery must be controlled.

Communication must be authenticated.

Authorization must determine which services a function is allowed to access.

In a cloud-native network, identity replaces physical location as one of the most important foundations of trust.

IDS and IPS

An Intrusion Detection System identifies suspicious activity.

An Intrusion Prevention System can additionally take action to block or disrupt malicious traffic.

Network Traffic | v Inspection | +--------+--------+ | | v v Legitimate Suspicious | | v v Allow Alert | v IPS Action

In telecom, IDS/IPS must understand more than generic IP traffic.

They need to understand the protocols and relationships that define mobile networks.

A system that knows only IP addresses and ports may miss important attacks hidden inside legitimate-looking signaling.

Telecom security requires protocol awareness. The packet payload often tells you more than the IP header.

Telecom Threat Detection

Effective threat detection begins with understanding what normal behavior looks like.

For example, a network may know:

  • Which signaling peers normally communicate
  • Which GTP endpoints are expected
  • Which network functions exist
  • Which ports and protocols they use
  • Which subscribers generate normal traffic patterns
  • Which signaling rates are expected

An anomaly can then be detected as a deviation from that model.

Normal Peer A | +---- Expected Signaling | +---- Expected Rate | +---- Expected Messages Anomaly Unknown Peer | +---- Unexpected Message | +---- High Rate | +---- Unexpected Destination | v ALERT

This is why telecom security monitoring is not simply traditional SOC monitoring with different IP addresses.

Security Monitoring

A mature telecom security architecture correlates information from multiple layers.

Security Monitoring ``` | +---------------+---------------+ | | | v v v ``` Signaling Network Infrastructure | | | v v v SS7/GTP IP/NIC OS/Kubernetes | | | +---------------+---------------+ | v Correlation | v Detection

For example, a security platform may detect:

A sudden increase in GTP traffic from an unexpected source.

At the same time, a network function may report an abnormal session rate.

The infrastructure may show increased CPU utilization.

Together, these events are far more meaningful than any individual alert.

One alert can be noise. Correlated behavior can become evidence.

Segmentation

Segmentation is one of the most important defensive controls in telecom.

The goal is simple:

Do not allow every component to communicate with every other component.

CORE ``` +---------------------------+ | | | Control Plane | | | +-------------+-------------+ | Controlled Path | +-------------v-------------+ | | | User Plane | | | +---------------------------+ Management Plane | X Restricted Access ```

Management traffic should not be freely accessible from subscriber networks.

User-plane traffic should not automatically have access to management systems.

External signaling peers should be restricted to the interfaces they actually require.

In Kubernetes environments, segmentation can also involve namespaces, network policies, dedicated interfaces, and infrastructure-level controls.

Zero Trust Principles in Telecom

The idea of zero trust becomes increasingly relevant to cloud-native telecom.

The basic principle is:

Never assume trust simply because the traffic is inside the network.

Every connection should be evaluated according to:

  • Identity
  • Source
  • Destination
  • Protocol
  • Context
  • Authorization
  • Expected behavior

This does not mean every packet must be individually authenticated in every telecom environment.

It means trust must be explicitly designed rather than assumed.

Hardening the Network

Hardening is the process of reducing unnecessary exposure and attack opportunities.

At the operating system level, this may include:

  • Removing unnecessary services
  • Applying security updates
  • Restricting administrative access
  • Using strong authentication
  • Protecting credentials
  • Configuring host firewalls
  • Monitoring privileged actions

At the network level:

  • Restrict management access
  • Filter signaling peers
  • Limit exposed ports
  • Apply ACLs
  • Segment networks
  • Monitor unexpected traffic

At the Kubernetes level:

  • Restrict API access
  • Use RBAC
  • Apply network policies
  • Secure container images
  • Minimize container privileges
  • Protect secrets
  • Monitor workloads
Every unnecessary service is another door. Every unnecessary privilege is another key.

Security in the User Plane

The user plane is different from the control plane.

Its primary job is to move traffic.

That makes visibility challenging.

Subscriber Traffic | v gNB | v GTP-U | v UPF | v Internet

Security systems must be able to determine whether traffic is legitimate without unnecessarily disrupting subscriber traffic.

This requires a balance between:

  • Visibility
  • Performance
  • Latency
  • Privacy
  • Detection quality

High-performance user-plane inspection can become a significant engineering challenge.

Security Versus Performance

This is particularly important in telecom.

A security function inserted into a high-speed data path can introduce:

  • Latency
  • CPU consumption
  • Packet drops
  • Throughput limitations
  • Additional failure points
Without Inspection Traffic | v UPF | v Network With Inspection Traffic | v UPF | v Security Function | v Network

The security architecture must therefore consider performance from the beginning.

A security control that takes the network down is not a successful security control.

Security and Cloud-Native Telecom

The move toward Kubernetes and cloud-native network functions introduces another security layer.

Application | Container | Pod | Kubernetes | CNI | Node | Operating System | Virtualization | Hardware

Every layer introduces potential vulnerabilities.

A secure application running inside an insecure container image is still exposed.

A secure container running on a compromised node is still exposed.

A secure node connected to an unrestricted network is still exposed.

Security is only as strong as the weakest trust boundary in the path.

Security Monitoring and Packet Analysis

Packet captures remain one of the most powerful tools available to a telecom security engineer.

The same tools used for troubleshooting can support security investigations.

Wireshark and TShark can reveal:

  • Unexpected signaling
  • Protocol violations
  • Unknown peers
  • Abnormal message sequences
  • Unexpected GTP traffic
  • Suspicious session behavior
Packet Capture ``` | v ``` Protocol Decode | v Message Sequence | v Expected Behavior? / YES NO | | v v Normal Investigate

The key is not merely seeing a packet.

The engineer must understand whether the packet makes sense in the context of the network.

Security Through Call Flows

Call-flow knowledge becomes extremely valuable during security investigations.

Suppose a normal session establishment follows a known sequence.

UE | | Registration / Attach v RAN | | Signaling v Core | | Authentication v Subscriber Database | | Session Establishment v SMF / MME | | Tunnel Creation v UPF / SGW | v User Traffic

An attack may appear as a deviation from this sequence.

For example:

  • A message appears before the expected authentication stage.
  • A signaling peer sends a message it should never originate.
  • A session is modified without the expected context.
  • A GTP tunnel appears without a legitimate control-plane relationship.
The strongest security analysts do not only ask whether a packet is valid. They ask whether the packet belongs in the story of the session.

Building a Telecom Security Mindset

A traditional network engineer may ask:

“Is the interface up?”

A security engineer asks:

“Should this interface be communicating with that endpoint at all?”

A troubleshooting engineer may ask:

“Why did this session fail?”

A security engineer may also ask:

“Who generated these requests, and why?”

Both perspectives are necessary.

The Convergence of Telecom and Cybersecurity

The modern telecom engineer increasingly operates at the intersection of several disciplines.

Telecom | +---------+---------+ | | v v Networking Security | | +---------+---------+ | v Cloud / DevOps | v Cloud-Native Telco

Understanding only one of these domains is no longer enough for complex 4G and 5G environments.

The engineer must understand the protocols.

The infrastructure.

The applications.

The trust relationships.

And the ways in which attackers can abuse all of them.

The modern telecom security engineer is not simply protecting servers. They are protecting the logic that allows the network to make decisions.

Security as a Continuous Process

Security is not a configuration that is completed once.

Networks evolve.

New interfaces are introduced.

New roaming relationships are created.

New software versions are deployed.

New cloud infrastructure is added.

New vulnerabilities are discovered.

Therefore, security must continuously evolve.

Design | v Deploy | v Monitor | v Detect | v Investigate | v Respond | v Harden | +-------> Back to Monitor
Security is not a wall around the network. It is a continuous feedback loop between architecture, visibility, detection, and response.

Chapter Takeaways

Mobile network security begins with architecture.

The control plane, user plane, management plane, and infrastructure all require different security considerations.

SS7, Diameter, and GTP have different roles and different attack surfaces.

GTP-C and GTP-U must be considered separately because they control and transport different aspects of the mobile service.

Signaling attacks can be particularly dangerous because a relatively small amount of traffic can trigger expensive processing.

4G introduced a more structured packet-core security architecture, while 5G expands the security surface into service-based interfaces, APIs, cloud-native infrastructure, and Kubernetes.

Network Function identity becomes increasingly important in 5G.

Segmentation reduces the blast radius of a compromise.

Hardening removes unnecessary exposure.

IDS and IPS provide visibility and response, but telecom security requires protocol awareness.

Packet analysis remains a fundamental capability for both troubleshooting and threat detection.

Most importantly, security analysis must understand context.

A packet is not suspicious because it is unusual. It is suspicious when it is unusual for where it came from, what it is doing, and when it is doing it.

The mobile network is a distributed system of trust.

Protecting it means understanding those relationships at protocol level, network level, application level, and infrastructure level.

When you understand how the network is supposed to behave, abnormal behavior becomes visible. When you understand why the network behaves that way, you can begin to understand how it can be attacked.

This foundation prepares us for the next stage of the architecture: connecting telecom security with cloud-native operations, observability, automation, and the operational systems required to protect a modern 4G/5G network at scale.

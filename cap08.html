Chapter 8: 5G Core Call Flows and Troubleshooting

From expected signaling to evidence-based diagnosis.

A call flow is not just a sequence of messages. It is the blueprint of what the network is supposed to do.

Understanding the architecture of the 5G Core is necessary. Understanding the Service-Based Architecture is necessary. Knowing the individual network functions is necessary.

But none of those skills, by themselves, make an engineer good at troubleshooting.

The real test begins when something fails.

A UE does not register. Authentication times out. A PDU session is rejected. The UE receives an IP address but cannot reach the Internet. The session is established, but user traffic never arrives.

At that point, architecture diagrams are no longer enough.

The engineer needs a model of the expected behavior.

That model is the call flow.

The fastest way to understand a failure is often to find the exact message where reality stopped matching the expected call flow.

Why Call Flows Matter

A mobile network is a state machine.

One event causes another. A message creates state. A response confirms or rejects an operation. A successful procedure enables the next procedure.

Registration | v Authentication | v Security Context | v PDU Session Establishment | v QoS / User Plane Setup | v User Traffic

If registration fails, there may be no usable context for later procedures.

If authentication fails, session establishment may never begin.

If PDU session establishment fails, the UE may be registered but have no data connectivity.

If the session succeeds but GTP-U does not work, signaling may look perfectly healthy while the subscriber still cannot access an application.

A successful procedure does not prove that the next procedure will succeed.

The Three Questions of Troubleshooting

Every troubleshooting investigation should begin with three questions:

What should have happened? What actually happened? Where did they become different?

The first question requires architectural knowledge.

The second requires observation.

The third requires engineering judgment.

Troubleshooting is the process of locating the first point where expected behavior and observed behavior diverge.

The 5G Registration Procedure

Before the UE can use the 5G Core normally, it must establish a registration context.

A simplified registration flow looks like this:

UE gNB AMF | | | |-- Registration Request -------->| | |--------------->| | | | |<-- Registration Accept ---------| | | | |-- Registration Complete ------->| | | |

The actual procedure contains additional messages and interactions, but the high-level model is useful.

The UE sends a NAS Registration Request.

The gNB transports the NAS message toward the AMF using NGAP signaling.

The AMF becomes the central control-plane function responsible for the access and mobility procedure.

NGAP and NAS

One of the first concepts an engineer must keep clear is the relationship between NAS and NGAP.

UE | | NAS | v gNB | | NGAP | v AMF | | NAS information | v UE

NAS messages are exchanged logically between the UE and the 5G Core.

NGAP provides the signaling relationship between the gNB and the AMF.

The gNB transports NAS signaling but does not become the endpoint of the NAS protocol.

When analyzing a registration failure, always distinguish the radio/access transport from the NAS procedure being transported.

Registration: What Should Happen?

A simplified registration sequence can be represented as:

UE | | Registration Request v gNB | | NGAP Initial UE Message v AMF | | Authentication v AUSF / UDM | | Authentication Result v AMF | | Security / Registration v UE | | Registration Complete v AMF

The exact signaling sequence can contain additional steps, security procedures, identity handling, and context establishment.

For troubleshooting, however, the engineer first needs to identify the major phases.

Registration Request | v Identity / Context | v Authentication | v Security | v Registration Accept | v Registration Complete

Authentication

Authentication is one of the first major control-plane dependencies.

The AMF does not perform the complete authentication process in isolation. It interacts with authentication and subscriber-data functions.

UE | | Authentication Request v AMF | | SBA v AUSF | | Subscriber Data v UDM | | Authentication Information v AUSF | | Authentication Result v AMF | v UE

This introduces several potential failure points.

  • UE identity problems
  • Authentication vector problems
  • UDM service failures
  • AUSF service failures
  • NF discovery problems
  • SBI connectivity problems
  • TLS or HTTP/2 failures
  • Authentication rejection

A registration failure is therefore not necessarily a radio problem.

The fact that the UE reached the AMF proves that the procedure started. It does not prove that the Core can authenticate the subscriber.

Registration Troubleshooting

Imagine the UE sends a Registration Request.

The gNB receives it.

The AMF receives the corresponding NGAP message.

Then nothing happens.

The engineer should not immediately blame the gNB.

Instead, reconstruct the flow.

UE | | Registration Request v gNB | | NGAP Initial UE Message v AMF | X | | No Authentication | v Procedure Stops

The key question becomes:

What was the AMF waiting for?

If the AMF attempted to contact the AUSF, inspect the SBA transaction.

If no request was generated, inspect the AMF logic and state.

If a request was generated but no response returned, inspect the network and the AUSF.

If a response returned with an error, inspect the application-level reason.

Never troubleshoot a timeout as a single event. Identify which transaction timed out and which function was expected to answer it.

PDU Session Establishment

Once the UE is registered, it can request a data session.

In 5G this is the PDU Session Establishment procedure.

UE | | PDU Session Establishment Request v gNB | | NAS / NGAP v AMF | | Session Management v SMF | | Policy / Selection v PCF | | Session Control v SMF | | N4 / PFCP v UPF | | User Plane Ready v SMF | v AMF | v UE

This procedure creates the logical state required for user-plane connectivity.

The SMF becomes central to the session-management process.

It determines how the session should be established and which UPF should be used.

UE → gNB → AMF → SMF → UPF

The simplest mental model for a 5G data session is:

UE | | NAS v gNB | | NGAP v AMF | | Session Management v SMF | | PFCP v UPF | | GTP-U v Data Network

Each step has a different responsibility.

  • UE requests connectivity.
  • gNB provides radio access and transports signaling and user traffic.
  • AMF handles access and mobility signaling.
  • SMF manages the PDU session.
  • UPF forwards user traffic.
The subscriber sees one connection. The network sees a chain of state transitions across multiple functions.

PFCP: Controlling the User Plane

The Packet Forwarding Control Protocol, or PFCP, is used between the SMF and UPF.

This is a critical distinction.

The SMF controls.

The UPF forwards.

SMF | | PFCP | v UPF | | GTP-U | v Network

The SMF can install or modify forwarding rules in the UPF.

Those rules determine how packets should be handled.

If PFCP signaling fails, the UPF may not have the required forwarding state.

The UE may therefore complete signaling procedures while user traffic remains broken.

A session can exist in the control plane while the user plane is still unable to carry packets.

PFCP Session Establishment

A simplified PFCP sequence looks like:

SMF UPF | | |---- PFCP Association ---------->| |<--- PFCP Association Response --| | | |---- Session Establishment ----->| | | |<--- Session Establishment Resp -| | |

The exact message sequence depends on the deployment and state of the UPF.

The important concept is that the SMF establishes the forwarding context required by the UPF.

The engineer should therefore correlate:

PDU Session Request | v SMF Session State | v PFCP Session | v UPF Forwarding State

GTP-U: Where the Packets Actually Travel

Once the user plane is established, subscriber traffic is transported using GTP-U.

The simplified path is:

UE | | IP Packet v gNB | | GTP-U v UPF | | IP v Data Network

The packet generated by the application is encapsulated inside GTP-U for transport across the mobile user plane.

This creates another critical troubleshooting distinction.

Control Plane NAS | NGAP | AMF | SMF | PFCP | UPF User Plane Application Packet | GTP-U | UPF | Data Network
If signaling is healthy but GTP-U is broken, the network can successfully establish a session that cannot actually carry data.

TEIDs and User-Plane Correlation

GTP-U uses a TEID, or Tunnel Endpoint Identifier, to identify tunnel context.

The TEID is extremely valuable during packet analysis.

GTP-U Packet | +---- Source IP | +---- Destination IP | +---- UDP | +---- GTP-U | +---- TEID | +---- Inner IP Packet

When investigating a user-plane failure, the engineer can use tunnel information to correlate packets with the session and forwarding state.

This is especially useful when many subscribers share the same infrastructure.

In a busy mobile core, the TEID helps turn “millions of packets” into “this subscriber's tunnel.”

QoS During Session Establishment

The PDU session is not only about connectivity.

It also establishes the framework for QoS treatment.

A simplified model is:

PDU Session | +---- QoS Flow | +---- QoS Flow | +---- QoS Flow | 5QI

Different flows can receive different treatment depending on policy and service requirements.

The SMF and PCF can participate in determining session and policy behavior.

The UPF then applies the user-plane rules associated with the session.

QoS is not a single setting. It is the result of policy, session state, forwarding rules, and radio treatment working together.

Control Plane Versus User Plane

One of the most important troubleshooting skills is separating these two planes.

5G CORE ``` CONTROL PLANE | +-----------+-----------+ | | | AMF SMF AUSF | PCF | NRF | UDM USER PLANE | UPF | GTP-U | Data Network ```

A control-plane problem can prevent a session from being created.

A user-plane problem can prevent traffic from flowing after the session exists.

The symptoms can look similar from the subscriber's perspective:

“The Internet does not work.”

But the underlying causes can be completely different.

Scenario: Registration Fails

Suppose the UE never reaches the registered state.

Start with the call flow.

UE | | Registration Request v gNB | | NGAP v AMF | | Authentication Request v AUSF | X | No Response

The failure boundary is between the AMF and AUSF.

Now investigate progressively.

AMF -> AUSF 1. NF discovery 2. Service endpoint 3. IP connectivity 4. TCP 5. TLS 6. HTTP/2 7. API request 8. API response 9. Authentication result

This prevents the investigation from becoming random.

Scenario: Registration Succeeds, PDU Session Fails

Now imagine registration is successful.

Registration SUCCESS Authentication SUCCESS Security SUCCESS PDU Session FAILURE

The investigation should move forward in the call flow.

UE | | PDU Session Request v AMF | | Nsmf v SMF | X | Session rejected

The likely investigation area has changed.

Now inspect:

  • SMF selection
  • NF discovery
  • Subscription data
  • Policy interaction
  • DNN configuration
  • Slice selection
  • UPF selection
  • SMF internal state

The successful registration is evidence.

It tells us which portions of the network have already demonstrated basic functionality.

Every successful stage eliminates entire classes of possible failures.

Scenario: PDU Session Succeeds, Internet Fails

This is one of the most important cases in mobile troubleshooting.

Registration SUCCESS Authentication SUCCESS PDU Session SUCCESS IP Address ASSIGNED PFCP SUCCESS GTP-U ? Internet FAILURE

At this point, continuing to investigate AMF registration logic is usually wasted effort.

The investigation should move toward the user plane.

UE | | IP Packet v gNB | | GTP-U v UPF | | N6 v Data Network | X Internet

Now ask:

  • Is GTP-U arriving at the UPF?
  • Is the expected TEID being used?
  • Does the UPF have the correct forwarding rules?
  • Is the inner UE IP correct?
  • Is routing correct toward the Data Network?
  • Is return traffic coming back?
  • Is NAT required and functioning?
  • Are firewall rules blocking the traffic?
  • Is DNS working?
Once the control plane proves that the session exists, stop treating the problem like a registration problem.

Packet Capture Strategy

Packet captures are among the most powerful tools available to a mobile-core engineer.

But a capture is useful only when interpreted in context.

The first step is to identify what interface or point in the architecture is being observed.

Capture Point ``` | +---- N2 / NGAP | +---- SBI / HTTP2 | +---- N4 / PFCP | +---- N3 / GTP-U | +---- N6 / Data Network ```

A capture taken on N2 answers different questions from a capture taken on N3.

A capture on an SBI answers different questions from a capture on N4.

A packet capture without architectural context is just a pile of packets.

Reading a Control-Plane Capture

Consider an N2 capture.

NGAP | +---- Initial UE Message | +---- Downlink NAS Transport | +---- Uplink NAS Transport | +---- Initial Context Setup | +---- UE Context Release

The engineer should reconstruct the sequence rather than inspecting individual packets in isolation.

Ask:

  • Which message started the procedure?
  • Which message should come next?
  • Did it arrive?
  • Was the response expected?
  • Did the network send a rejection?
  • Did the procedure stop after a timeout?

This is how packet analysis becomes call-flow analysis.

Reading an SBI Capture

Now consider an AMF-to-AUSF transaction.

TCP | TLS | HTTP/2 | Request | Response

Do not jump directly to the JSON payload.

First verify that the lower layers are functioning.

Then inspect the HTTP/2 transaction.

Finally inspect the application-level content.

Layer Question IP Can the endpoints communicate? TCP Was the connection established? TLS Was the secure session established? HTTP/2 Was the SBI channel established? API Was the request valid? Application Was the operation successful?
Always troubleshoot from the bottom up, but interpret the result from the top down.

Reading PFCP Captures

PFCP captures provide direct evidence of SMF-UPF interaction.

SMF UPF | | |---- Association Request ------>| |<--- Association Response ------| | | |---- Session Establishment ---->| |<--- Session Establishment Resp-| | | |---- Session Modification ----->| |<--- Session Modification Resp-| | |

If the SMF believes the UPF is configured but the UPF has no matching forwarding state, the capture can reveal where the state installation process failed.

This is particularly important when the control plane appears healthy.

Reading GTP-U Captures

Now move to the user plane.

gNB UPF | | |---- GTP-U ----------------->| | TEID: XXXXX | | Inner IP: 10.x.x.x | | | |<---- GTP-U ------------------| | TEID: YYYYY | | Inner IP: 10.x.x.x | | |

The engineer should verify:

  • Source and destination addresses
  • UDP ports
  • GTP-U headers
  • TEIDs
  • Inner IP addresses
  • Packet direction
  • Sequence behavior when relevant
  • Whether packets return

A packet appearing in one direction but not the other is powerful evidence.

The absence of a packet is also a packet-analysis result.

Following One Subscriber

Large networks generate enormous volumes of signaling.

A troubleshooting engineer cannot analyze everything.

The investigation therefore needs correlation.

Possible identifiers include:

  • Subscriber identity
  • SUPI / SUCI-related context
  • UE identifiers
  • PDU Session ID
  • TEID
  • IP address
  • Transaction identifiers
  • Timestamp

The objective is to transform:

“Something is wrong in the network.”

into:

“Subscriber X created PDU Session Y, which selected UPF Z, but the expected GTP-U tunnel was not established.”
Good troubleshooting reduces a distributed system to one reproducible transaction.

Time Is Evidence

Timestamps are extremely valuable.

Consider:

10:15:00.001 Registration Request 10:15:00.010 AMF receives UE context 10:15:00.020 Authentication request 10:15:00.025 SBI request 10:15:00.030 SBI response 10:15:00.050 Registration Accept 10:15:01.200 PDU Session Request 10:15:01.250 SMF selected 10:15:01.300 PFCP Session Establishment 10:15:01.320 PFCP response 10:15:01.350 Session Accept 10:15:02.000 First GTP-U packet

Now imagine the PFCP response never appears.

The timeline immediately identifies a likely failure boundary.

This is why synchronized clocks and accurate timestamps matter in distributed networks.

In a distributed system, time is not decoration. Time is correlation.

Building the Failure Boundary

One of the most powerful techniques in troubleshooting is to identify the failure boundary.

For example:

UE | | SUCCESS v gNB | | SUCCESS v AMF | | SUCCESS v SMF | | SUCCESS v UPF | | FAILURE v Data Network

The investigation should concentrate around the first boundary where expected behavior is no longer observed.

Do not treat every component equally.

The closer you locate the first failure boundary, the smaller the problem becomes.

Control Plane Failure Matrix

A practical mental model is:

Symptom | +---- No Registration | | | +---- Radio / gNB | +---- NGAP | +---- AMF | +---- Authentication | +---- SBA | +---- Registration OK | +---- PDU Session Failure | +---- AMF +---- SMF +---- Policy +---- Subscriber Data +---- UPF Selection +---- Slice / DNN

This does not replace detailed troubleshooting.

It provides a starting hypothesis.

User Plane Failure Matrix

PDU Session Established | v No Data | +---- No GTP-U | +---- Wrong TEID | +---- UPF Rules | +---- Routing | +---- NAT | +---- Firewall | +---- DNS | +---- Return Path

Again, the important point is to move from symptom to evidence.

Do not assume the UPF is broken simply because the subscriber has no Internet.

The problem may exist outside the mobile core entirely.

End-to-End Troubleshooting

A complete investigation should follow the subscriber's traffic from origin to destination.

CONTROL PLANE UE | | Registration v gNB | v AMF | +---- AUSF | +---- UDM | +---- SMF | +---- PCF | v Session Established ``` USER PLANE ``` UE | v gNB | | GTP-U v UPF | | IP v Data Network | v Application

The engineer should verify each major transition.

A successful control-plane procedure establishes the conditions for the user plane.

The user plane then proves whether those conditions actually work.

The Most Dangerous Assumption

One of the most common troubleshooting mistakes is assuming:

“Because the session was established, the network is working.”

That assumption is dangerous.

Session establishment proves that a sequence of control-plane operations succeeded.

It does not automatically prove:

  • Correct UPF forwarding
  • Correct routing
  • Working GTP-U in both directions
  • Working NAT
  • Working DNS
  • Working external connectivity
  • Application reachability
Control-plane success creates possibility. User-plane traffic provides proof.

Wireshark and TShark

Packet-analysis tools such as Wireshark and TShark are essential for this kind of investigation.

Wireshark provides interactive inspection and protocol decoding.

TShark provides command-line packet analysis and automation capabilities.

The important skill is not simply knowing how to open a capture.

It is knowing what to search for.

Capture | +---- Subscriber | +---- Timestamp | +---- Protocol | +---- Procedure | +---- Transaction | +---- Failure

An experienced engineer does not scroll through thousands of packets hoping to discover a problem.

The engineer forms a hypothesis and uses the capture to prove or disprove it.

Packet analysis is not packet browsing. It is hypothesis testing with network evidence.

Call Flow as a Diagnostic Tool

Suppose a subscriber reports:

“My phone shows 5G, but I have no Internet.”

That statement is not a diagnosis.

It is a symptom.

The engineer should translate it into a sequence of technical questions.

5G Radio Available? | v Registration Successful? | v Authentication Successful? | v PDU Session Established? | v IP Address Assigned? | v PFCP State Installed? | v GTP-U Packets Present? | v UPF Forwarding? | v External Routing? | v DNS? | v Application?

Every successful answer narrows the search space.

Every failed answer defines the next investigation.

From Symptom to Root Cause

Consider a hypothetical case.

Symptom: No Internet Evidence: Registration = SUCCESS Authentication = SUCCESS PDU Session = SUCCESS IP Assignment = SUCCESS PFCP = SUCCESS GTP-U Uplink = SUCCESS GTP-U Downlink = NO RESPONSE

The investigation should now focus on the downlink path.

Internet | v Data Network | X | UPF | v GTP-U | v gNB | v UE

Possible causes now include:

  • Incorrect return routing
  • Missing UPF forwarding rule
  • Wrong downlink tunnel information
  • Firewall filtering
  • NAT behavior
  • External network failure

Notice what is no longer at the top of the list:

“Maybe the UE failed to register.”

The evidence has already disproved that hypothesis.

Good troubleshooting is not about finding more possibilities. It is about eliminating possibilities with evidence.

The Engineer's Mental Model

A strong 5G Core engineer constantly maintains two models.

MODEL 1 What should happen? ``` Call Flow | v ``` Expected State
MODEL 2 What actually happened? ``` Packet Capture + Logs / Metrics + Counters | v Observed State ```

Troubleshooting is the comparison between those two models.

Expected State | | v Compare ^ | | Observed State ``` | v ``` First Divergence | v Failure Boundary | v Root Cause
The call flow tells you where you should be. The packets tell you where you actually are.

Chapter Takeaways

5G Core troubleshooting begins with understanding expected call flows.

The major procedures include:

  • Registration
  • Authentication
  • PDU Session Establishment
  • QoS and policy establishment
  • User-plane activation

The simplified path:

UE | v gNB | v AMF | v SMF | v UPF | v Data Network

does not mean that every message travels through every function. It means that these functions participate in different parts of the overall service.

NGAP carries signaling between the gNB and AMF.

NAS provides UE-to-core signaling for procedures such as registration and session management.

SBA allows core functions to communicate through service-based interactions.

PFCP controls the forwarding state between SMF and UPF.

GTP-U carries subscriber user-plane traffic.

QoS determines how different traffic flows are treated.

The most important troubleshooting principle is to separate control-plane and user-plane failures.

CONTROL PLANE Registration | Authentication | PDU Session | PFCP | Session State USER PLANE IP Packet | GTP-U | UPF | Data Network | Application

When investigating a failure, reconstruct the call flow.

Identify what should have happened.

Compare it with what actually happened.

Find the first divergence.

Then investigate the smallest possible failure domain.

Do not start by asking “what is broken?” Start by asking “what was the last thing that worked?”

That single question can transform a complex 5G Core incident into a manageable investigation.

The strongest engineers do not memorize every possible failure. They understand the architecture well enough to determine which failures are possible, then use evidence to eliminate them.

A call flow is the story of a successful network. Troubleshooting is discovering where that story stopped being true.

With the 5G Core understood as a set of distributed functions and call flows understood as state transitions, the next challenge becomes operational: how do these network functions actually run at scale?

That question takes us from telecom architecture into the infrastructure underneath it: virtual machines, containers, Linux networking, Kubernetes, CNFs, CNI, and the cloud-native platform on which the modern 5G Core depends.

The future of troubleshooting is not choosing between telecom knowledge and software knowledge. It is combining both to follow the failure all the way to its source.

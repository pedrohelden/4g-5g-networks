Chapter 13: Network Testing, Deployment and Migration

From controlled laboratory validation to production rollout and large-scale mobile network migration.

A network is not ready for production because it works. It is ready because we have evidence that it will continue to work when reality begins.

Designing a telecom network is only part of the engineering challenge.

Operating it safely is another.

Between a design document and a production network there is a critical engineering discipline: testing, validation, deployment, and migration.

This discipline becomes particularly important in mobile networks because the infrastructure is highly interconnected.

A change to one component can affect signaling, user-plane traffic, routing, subscriber services, security, charging, mobility, and ultimately thousands or millions of subscribers.

In telecom, a change is never isolated just because the configuration is isolated.

Lab and Production Are Different Worlds

A laboratory environment exists to provide controlled conditions.

Production exists to serve real customers.

The distinction sounds obvious, but it has profound consequences.

LAB Controlled | +---- Known traffic | +---- Limited subscribers | +---- Controlled failures | +---- Repeatable tests | v Validation PRODUCTION Real users | +---- Unknown traffic patterns | +---- Real dependencies | +---- Operational constraints | +---- Business impact | v Service

A test that succeeds in the laboratory does not automatically guarantee production success.

The lab should reduce uncertainty.

It cannot eliminate reality.

What a Good Lab Should Prove

A telecom laboratory should answer specific engineering questions.

  • Does the component start correctly?
  • Can it communicate with its peers?
  • Are interfaces configured correctly?
  • Are signaling procedures successful?
  • Can sessions be established?
  • Does user traffic flow correctly?
  • Does the system behave correctly under failure?
  • Does performance remain acceptable under expected load?

The laboratory is therefore not simply a place where engineers make configurations.

It is a place where assumptions are challenged.

The purpose of a lab is not to prove that the engineer is right. It is to discover where the design is wrong before production does it for us.

Testing should be structured around test cases rather than informal experimentation.

Without explicit expectations, it becomes difficult to determine where a failure actually occurred.

Validation

Validation asks a fundamental question:

Does the implementation satisfy the intended design?

Validation can occur at multiple levels.

Design | v Configuration | v Component | v Interface | v End-to-End Service

A component can pass its individual validation while the complete service fails.

For example, an SMF may be healthy.

A UPF may be healthy.

PFCP connectivity may be established.

And yet the subscriber may still be unable to access the internet because of an IP routing or DNS problem.

Component validation proves components. End-to-end validation proves the service.

Integration Testing

Telecom systems rarely operate alone.

Integration testing verifies that independently developed components work together.

AMF | +------ AUSF | +------ UDM | +------ SMF | +------ PCF | +------ UPF | v Network

Every interface introduces another possible failure domain.

Integration testing therefore needs to verify:

  • Connectivity
  • Protocol compatibility
  • Message sequences
  • Timeout behavior
  • Error handling
  • Configuration consistency
  • Security policies

The objective is not simply to prove that two systems can communicate.

It is to prove that they communicate correctly under normal and abnormal conditions.

Negative Testing

A mature test strategy does not test only successful scenarios.

It deliberately creates failures.

Examples include:

  • Removing an interface
  • Blocking a signaling port
  • Stopping a network function
  • Introducing packet loss
  • Introducing latency
  • Restarting a container
  • Removing a route
  • Providing invalid configuration
Normal Operation | v Failure Injection | v System Reaction | +---- Detection | +---- Recovery | +---- Failover | +---- Alerting | v Service Restored

This is especially important for high-availability systems.

A redundant architecture is not truly redundant until failover has been tested.

Redundancy that has never been tested is an assumption, not a guarantee.

Performance Testing

Functional correctness is only one dimension of validation.

A system can perform the correct procedure and still fail under realistic traffic.

Performance testing examines how the network behaves under load.

Typical dimensions include:

  • Throughput
  • Packets per second
  • Concurrent sessions
  • Transaction rate
  • Latency
  • CPU utilization
  • Memory utilization
  • Packet loss
Load ``` | v +------------------+ | Network Function | +------------------+ | | | v v v CPU Memory Traffic | | | +------+------+ | v Performance ```

Telecom performance testing must also consider signaling load.

A system can have enough bandwidth but still be overloaded by control-plane transactions.

Conversely, it can process signaling correctly while struggling with user-plane throughput.

Capacity is not one number. It is the relationship between workload, resources, latency, and service quality.

Baseline Testing

Before making a major change, engineers should understand the current state of the network.

This is the baseline.

Before Change KPIs KQIs CPU Memory Sessions Latency Packet Loss Errors Routes Neighbors Signaling Traffic ``` | v BASELINE ```

Without a baseline, post-change validation becomes subjective.

After the change, the engineer needs something against which to compare the new state.

Pre-Checks

Pre-checks establish whether the environment is safe for the change.

Typical checks may include:

  • Current alarms
  • Interface status
  • Routing tables
  • CPU and memory utilization
  • Active sessions
  • Signaling health
  • Peer connectivity
  • Cluster health
  • Backup availability
  • Configuration consistency
PRE-CHECK System Healthy? | +---- NO ----> Stop | +---- YES | v Continue Change

This simple decision is extremely important.

A change should not be performed on top of an already unstable system unless there is a clear incident-management reason to do so.

Never use an unstable baseline to validate a change.

Change Management

Production changes require more than technical preparation.

They require operational control.

A good change plan defines:

  • Objective
  • Scope
  • Dependencies
  • Implementation steps
  • Expected impact
  • Validation steps
  • Rollback procedure
  • Communication plan
  • Maintenance window
CHANGE REQUEST | v Technical Review | v Risk Assessment | v Approval | v Implementation | v Validation | +---- PASS ----> Close | +---- FAIL ----> Rollback

The rollback procedure deserves special attention.

A change without a tested rollback strategy is incomplete.

The safest deployment is not the one that never fails. It is the one that can fail without becoming an uncontrolled incident.

Rollback Strategy

Rollback should not be an improvised reaction to failure.

It should be designed before implementation begins.

New Configuration | v Deployment | v Validation | +---+---+ | | PASS FAIL | | v v Continue Rollback | v Restore Baseline | v Validate

A rollback plan should answer:

  • What exactly will be reverted?
  • How long will rollback take?
  • What dependencies are affected?
  • How will success be verified?
  • Who has authority to initiate rollback?

Deployment Strategy

Large telecom networks should rarely be changed everywhere simultaneously.

A safer approach is progressive deployment.

Lab | v Pilot | v Limited Region | v Small Production Group | v Regional Rollout | v National Rollout | v Full Deployment

Each stage provides additional evidence.

If something fails early, the blast radius remains limited.

The safest rollout is the one that discovers failure while the failure is still small.

Pilot Deployment

A pilot introduces the change to a controlled subset of the production environment.

The pilot should be representative enough to expose real-world behavior.

It should also be small enough to limit customer impact.

Production Network +----------------------------------+ | | | Region A Region B Region C| | | | NORMAL PILOT NORMAL | | | | | v | | Observe | | | | | v | | Validate | | | +----------------------------------+

Only after the pilot behaves as expected should the rollout expand.

4G to 5G Migration

The transition from 4G to 5G is not simply a radio upgrade.

It can involve changes across the entire architecture.

4G UE | v eNodeB | v EPC | +---- MME +---- SGW +---- PGW +---- HSS +---- PCRF 5G UE | v gNB | v 5G Core | +---- AMF +---- SMF +---- UPF +---- UDM +---- AUSF +---- PCF +---- NRF +---- NSSF

Migration therefore affects architecture, interfaces, signaling, subscriber data, policy, security, operations, monitoring, and troubleshooting.

NSA as a Migration Path

5G Non-Standalone architecture allows operators to introduce 5G radio capabilities while retaining the EPC as the core anchor.

NSA ``` UE | +------+------+ | | LTE NR eNodeB gNB | | +------+------+ | EPC | MME / SGW / PGW ```

This architecture can reduce the complexity of the initial 5G rollout because the existing EPC remains part of the architecture.

It also provides an important migration path toward a future standalone architecture.

NSA allows operators to introduce 5G without requiring the entire network to become 5G on day one.

NSA to SA Migration

Moving from NSA to Standalone introduces a deeper architectural transformation.

NSA UE | gNB | EPC | MME / SGW / PGW ``` | | Migration v ``` SA UE | gNB | 5G Core | +---- AMF +---- SMF +---- UPF +---- UDM +---- AUSF +---- PCF +---- NRF +---- NSSF

The migration changes the control-plane architecture and introduces the Service-Based Architecture of the 5G Core.

It also introduces new operational requirements.

The network now depends heavily on cloud-native infrastructure, service discovery, APIs, distributed logging, container orchestration, and new observability mechanisms.

The migration from NSA to SA is not merely a network-function replacement. It is an operational transformation.

Migration Planning

A migration should be decomposed into manageable phases.

Current State | v Dependency Mapping | v Target Architecture | v Compatibility Analysis | v Lab Validation | v Pilot | v Progressive Rollout | v Optimization | v Target State

Dependency mapping is especially important.

Before replacing a component, engineers need to understand what depends on it.

For example:

  • Signaling peers
  • Subscriber databases
  • Policy systems
  • Charging systems
  • DNS
  • Routing
  • Security controls
  • Monitoring platforms
  • External service providers

Pre-Deployment Checklist

Before deployment begins, the engineer should be able to answer:

  • What is changing?
  • Why is it changing?
  • What systems depend on it?
  • What is the expected behavior?
  • What is the current baseline?
  • How will success be measured?
  • What could fail?
  • How will failure be detected?
  • How will the change be rolled back?

If these questions cannot be answered, the deployment is not ready.

Post-Deployment Checks

Post-checks verify that the network returned to a healthy operational state.

POST-CHECK Interfaces | v Routing | v Signaling | v Sessions | v User Plane | v KPIs | v Alarms | v Customer Experience

The checks should compare against the pre-change baseline.

For example:

If session success was 99.7% before deployment and 99.7% afterward, that is evidence of stability.

If session success dropped to 94%, the deployment requires investigation even if the changed component reports itself as healthy.

Deployment Troubleshooting

Troubleshooting during deployment is different from troubleshooting a normal incident.

There is a known event:

A change was introduced at a specific time.

That provides a valuable correlation point.

Change Start | v Configuration Applied | v Behavior Changes | v Alarm / KPI Change | v Investigation

The challenge is determining whether the observed problem is actually caused by the deployment.

Temporal correlation is evidence.

It is not automatically proof.

A problem that begins after a change is suspicious. A problem that can be reproduced by the change is evidence.

Deployment Failure Patterns

Several failure patterns appear repeatedly during network deployment.

Configuration mismatch

Two components may be individually correct but configured with incompatible parameters.

AMF | | Expected: | 10.10.10.20 | X | | Configured: | 10.10.10.30 | v SMF

The result may appear as a generic connectivity failure even though both systems are operational.

Routing problems

A newly deployed function may have correct IP addresses but incorrect routing.

Firewall problems

A signaling port may be blocked even though both endpoints are reachable.

DNS problems

Cloud-native systems frequently depend on service discovery and DNS.

A DNS failure can therefore appear as an application or network-function failure.

Resource exhaustion

A deployment may succeed but consume more CPU, memory, or network resources than expected.

Unexpected traffic behavior

Real production traffic may behave differently from laboratory traffic.

Production is the final test of every assumption made in the lab.

Observability During Deployment

Monitoring should be increased, not reduced, during critical changes.

Before Change | v Baseline Monitoring | v Deployment | v Enhanced Monitoring | +---- Metrics +---- Logs +---- Traces +---- Signaling +---- Packet Capture | v Validation

The deployment window should be treated as a period of heightened observability.

This is especially important when introducing new cloud-native network functions.

Canary Deployments

Canary deployment extends the pilot concept.

A small percentage of traffic is exposed to the new version while the remainder continues to use the stable version.

Traffic | +-----+-----+ | | v v Stable Path New Path | | 95% 5% | | +-----+-----+ | v Monitoring | +-----+-----+ | | Healthy Failure | | v v Increase Rollback Exposure

This provides a controlled way to discover problems before full deployment.

Migration Is a Process, Not an Event

A common mistake is to treat migration as a single maintenance window.

In reality, migration is a lifecycle.

PLAN | v TEST | v VALIDATE | v PILOT | v DEPLOY | v MONITOR | v OPTIMIZE | v STANDARDIZE

Each stage reduces uncertainty.

Each stage creates evidence.

Each stage should improve the confidence of the next stage.

A successful migration is not the absence of incidents. It is controlled progress toward a known target state.

Operational Readiness

A system should not be considered ready simply because the software installation succeeded.

Operational readiness includes:

  • Monitoring
  • Alerting
  • Documentation
  • Backup
  • Rollback
  • Capacity planning
  • Security controls
  • Troubleshooting procedures
  • Support team readiness
Technical Readiness + Operational Readiness + Support Readiness + Security Readiness | v Production Readiness

This distinction becomes increasingly important as telecom networks become more software-driven.

Deployment as an Engineering Experiment

Every controlled deployment can be viewed as an experiment.

There is:

  • A known starting state
  • A controlled change
  • An expected outcome
  • Observable measurements
  • A decision based on evidence
BASELINE | v HYPOTHESIS | v CHANGE | v MEASURE | v COMPARE | +---- Expected ----> Continue | +---- Unexpected ---> Investigate

This mindset is powerful because it prevents deployment from becoming a sequence of blind configuration changes.

Every production change should answer three questions: What do we expect? How will we know? What will we do if we are wrong?

When Things Go Wrong

Even well-planned deployments can fail.

The response should remain structured.

Failure Detected | v Stop Further Changes | v Assess Impact | v Protect Service | v Collect Evidence | v Determine Cause | +---- Known / Safe ---> Fix | +---- Unknown -------> Rollback | v Validate Recovery | v Document Findings

The worst response to a deployment problem is uncontrolled experimentation.

Changing several parameters simultaneously destroys the evidence needed to understand the failure.

When production is failing, the first objective is not to change something. The first objective is to regain control.

Post-Incident Learning

A deployment failure should generate more than a fix.

It should generate knowledge.

After recovery, engineers should ask:

  • What happened?
  • Why was it not detected earlier?
  • Which assumption was incorrect?
  • Which test should have caught it?
  • Was the rollback sufficient?
  • Did monitoring provide enough evidence?
  • Should the deployment procedure change?

This creates a feedback loop.

Production Incident | v Root Cause | v Lesson Learned | v Test Case Updated | v Deployment Procedure Improved | v Future Deployment | v Lower Risk

The Senior Engineer's Perspective

Senior network engineering is not only about knowing protocols.

It is about understanding risk.

A technically correct change can still be operationally wrong if it is introduced without sufficient validation, monitoring, rollback, or communication.

The senior engineer therefore thinks beyond the configuration itself.

They ask:

What happens to the rest of the network?

What happens to existing sessions?

What happens during failure?

What happens if the deployment stops halfway?

What happens if the new component is healthy but the integration is not?

What happens at scale?

And most importantly:

How do we know?

Engineering confidence should come from evidence, not optimism.

Closing Perspective

Testing, deployment, and migration are where architecture becomes reality.

A design document describes what the network should be.

A laboratory demonstrates what it can do.

Integration testing demonstrates that components can work together.

Performance testing demonstrates that the system can handle realistic workloads.

A pilot demonstrates that the design survives real production conditions.

Progressive rollout controls the blast radius.

Monitoring provides evidence.

Rollback provides safety.

And post-deployment validation proves whether the network actually reached the intended state.

DESIGN | v LAB | v VALIDATION | v INTEGRATION | v PERFORMANCE | v PILOT | v DEPLOYMENT | v MONITORING | v VALIDATION | +---------+---------+ | | SUCCESS FAILURE | | v v EXPAND ROLLBACK | | v v FULL ROLLOUT INVESTIGATE | | +---------+---------+ | v LESSONS LEARNED | v BETTER NEXT CHANGE
The objective of deployment is not to make a change. The objective is to reach a new operational state with confidence.

This is the discipline that allows large telecom networks to evolve without turning every transformation into an operational risk.

Test before you trust. Validate before you scale. Monitor while you change. Roll back when the evidence says you should.

That is how networks evolve safely.

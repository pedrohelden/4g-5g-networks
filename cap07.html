Chapter 7: 5G Service-Based Architecture

From network nodes and fixed interfaces to software functions, services, and dynamic discovery.

The most important change in the 5G Core is not what the network functions are. It is how they communicate.

The previous chapter introduced the major functions of the 5G Core: AMF, SMF, UPF, UDM, AUSF, PCF, NRF, and NSSF.

Knowing the names of those functions is necessary, but it is not enough.

To understand how a modern 5G Core actually operates, we need to understand the architectural principle that connects them: Service-Based Architecture, or SBA.

SBA represents one of the biggest conceptual changes between the LTE EPC and the 5G Core.

The EPC was designed around network elements communicating through well-defined interfaces. The 5GC introduces a model where network functions expose services that other authorized network functions can consume.

This makes the 5G Core look much more like a distributed software system than a collection of traditional telecom appliances.

The 5G Core is a telecom network built with the architectural ideas of modern distributed software.

From Nodes to Services

Consider a simplified EPC architecture.

EPC ``` +------+ +------+ +------+ | MME |-------| SGW |-------| PGW | +------+ +------+ +------+ | | +------+ | HSS | +------+ ``` Communication is defined through specific network interfaces.

The relationships are relatively static.

The engineer knows which network element provides a particular function and which interface is used to reach it.

The 5GC takes a different approach.

5G Core ``` +------+ +------+ +------+ | AMF | | SMF | | AUSF | +------+ +------+ +------+ | | | +--------------+--------------+ | Service-Based Interfaces | +-------+-------+ | | | UDM PCF NRF ```

Instead of thinking primarily:

“AMF connects to function X through interface Y.”

we begin thinking:

“AMF consumes a service provided by another network function.”

This distinction may sound subtle. It is not.

It fundamentally changes how the network can be deployed, scaled, discovered, upgraded, and troubleshot.

What Is Service-Based Architecture?

A Service-Based Architecture is an architectural model in which network functions expose capabilities as services.

Other authorized network functions can discover those services and invoke them through defined service interfaces.

Network Function ``` +-------+ | AMF | +-------+ | Exposes Services | v +---------------------+ | Registration / | | Mobility Services | +---------------------+ | ^ | Consumed by other Network Functions ```

The network function is therefore more than a box performing a procedure.

It becomes a software component exposing capabilities to the rest of the network.

A network function does not simply exist. It advertises what it can do and provides services that other functions can consume.

Network Functions

The term Network Function, or NF, is central to the 5G architecture.

A Network Function provides one or more capabilities within the 5G Core.

Examples include:

  • AMF — Access and Mobility Management Function
  • SMF — Session Management Function
  • UDM — Unified Data Management
  • AUSF — Authentication Server Function
  • PCF — Policy Control Function
  • NRF — Network Repository Function
  • NSSF — Network Slice Selection Function
  • UPF — User Plane Function

A Network Function does not necessarily correspond to one physical appliance.

It can be implemented as software running on virtual machines, containers, bare-metal servers, or specialized infrastructure.

This is one of the reasons the 5G Core fits naturally into cloud-native environments.

When the network function becomes software, deployment becomes a software engineering problem as well as a telecom engineering problem.

Service-Based Interfaces

The communication mechanisms between 5G network functions are described using Service-Based Interfaces, commonly abbreviated as SBIs.

Examples include:

AMF | | Namf v AMF Services AMF | | Nsmf v SMF Services AMF | | Nausf v AUSF Services AMF | | Nudm v UDM Services SMF | | Npcf v PCF Services Network Functions | | Nnrf v NRF Services

The naming convention itself is useful.

The first letter identifies the consumer function. The following portion identifies the service provided by another function.

For example, Nsmf represents the service-based interface through which another function interacts with the SMF services.

These interfaces are defined by 3GPP specifications and are implemented using web-oriented technologies.

HTTP/2

One of the most important technologies behind the 5G SBA is HTTP/2.

Traditional telecom engineers may initially associate HTTP with web browsing.

In the 5G Core, HTTP/2 becomes part of the communication infrastructure between network functions.

5G Network Function ``` | | HTTP/2 | v Service-Based Interface | v Another Network Function ```

HTTP/2 provides features well suited to service-based communication, including multiplexed streams, header compression, and efficient connection handling.

This is very different from the signaling technologies that dominated earlier mobile cores.

LTE engineers are accustomed to protocols such as:

S1AP GTP-C Diameter SCTP

5G introduces another important layer:

HTTP/2 | REST-style APIs | JSON | Service-Based Interfaces | 5G Network Functions

This does not mean that all 5G signaling has become HTTP.

Protocols such as NAS and NGAP remain fundamental. GTP-U remains central to the user plane.

Rather, HTTP/2 becomes a major transport for communication between 5GC network functions over the SBA.

5G did not replace telecom protocols with HTTP. It added a software-service layer to the mobile core.

REST APIs

The SBA uses APIs following REST principles for service interactions.

These APIs allow network functions to request operations from other network functions in a structured and standardized way.

Conceptually:

AMF | | HTTP/2 Request | v AUSF | | HTTP/2 Response | v AMF

A request can carry structured information describing the operation and its parameters. Responses return structured information describing the result.

JSON is commonly used as the representation format for these SBI messages.

HTTP/2 | +---- HTTP Request | +---- Headers | +---- JSON Payload | +---- HTTP Response | +---- Status +---- Headers +---- JSON Payload

For a telecom engineer, this creates a new troubleshooting dimension.

It is no longer enough to ask:

“Is the IP connection between the two network functions up?”

We may also need to ask:

  • Is the service endpoint registered?
  • Can the consumer discover the provider?
  • Is the correct URI being used?
  • Is HTTP/2 functioning?
  • Is TLS configured correctly?
  • Is authentication succeeding?
  • Is the API request valid?
  • Is the remote function returning an error?
In a service-based core, “ping works” proves very little.

NRF: The Directory of the 5G Core

The Network Repository Function, or NRF, is one of the most important functions in the SBA.

Its role includes maintaining information about available network functions and supporting discovery.

A simplified model is:

NRF | +---------+---------+ | | | AMF SMF AUSF | | | Register Register Register | | | +---------+---------+ | Discovery

When a network function becomes available, it can register its profile with the NRF.

That profile can contain information such as:

  • NF type
  • NF instance information
  • Supported services
  • Service endpoints
  • IP addressing information
  • Availability information
  • Additional attributes required for discovery and selection

Other network functions can then discover the services they require.

The NRF allows the 5G Core to discover capabilities dynamically instead of depending entirely on hard-coded relationships.

NF Registration

Before a network function can participate fully in an SBA environment, it needs to make its presence and capabilities known.

Conceptually:

NRF | | NF Registration ^ | | AMF AMF tells the NRF: “I am an AMF instance. Here are my services. Here is where they are available.”

The NRF stores this information.

Other functions can then use discovery mechanisms to find the AMF or another required function.

This creates a dynamic relationship between network functions.

NF Discovery

Suppose the SMF needs to interact with a particular service provided by another network function.

Instead of relying only on a static configuration, the consumer can perform service discovery.

Consumer NF | | "I need a service of type X" | v NRF | | Matching NF instances | v Provider NF | | Service Endpoint | v Consumer NF

The discovery process can return one or more suitable network-function instances.

This becomes particularly important in large deployments where multiple instances of the same network function may exist.

NRF | +------------+------------+ | | | AMF-01 AMF-02 AMF-03 | | | +------------+------------+ | Available Services

A consumer can then select an appropriate instance based on the discovery information and selection logic.

Once you have hundreds of software instances, static configuration stops scaling. Discovery becomes infrastructure.

AMF and AUSF Interaction

A common example of SBA interaction occurs during subscriber authentication.

The UE communicates with the AMF through the access network. The AMF then interacts with the AUSF for authentication-related processing.

UE | | Registration v gNB | | NAS v AMF | | Nausf | HTTP/2 v AUSF | | Authentication data v UDM | v Authentication Result | v AMF | v UE

The important point is that the AMF does not need to contain all authentication logic itself.

It consumes authentication services provided by another function.

SBA turns complex procedures into chains of service interactions.

AMF and UDM Interaction

The AMF may also consume services from the UDM for subscriber-related information.

AMF | | Nudm | v UDM | v Subscriber Data Authentication Registration Data

This separation allows subscriber data management to evolve independently from access and mobility management.

It also means that troubleshooting may require correlation across multiple network functions.

SMF and PCF Interaction

The SMF manages PDU sessions, but policy decisions can influence how those sessions are handled.

The SMF can therefore interact with the PCF.

UE | | PDU Session Request v AMF | | Session Management v SMF | | Policy Request v PCF | | Policy Decision v SMF | | Session Rules v UPF

The policy result can influence QoS and other session behavior.

This demonstrates another important principle:

No single network function needs to know everything. The architecture distributes intelligence across specialized services.

SMF and UPF: Control Meets Forwarding

The SMF is responsible for controlling the user-plane behavior while the UPF performs the actual packet forwarding.

CONTROL ``` SMF | | N4 | v UPF | | USER PLANE ```

The N4 interface is not simply another generic SBI.

It is a dedicated control interface between the SMF and UPF, commonly using PFCP.

This distinction is important.

The 5G Core contains both:

  • Service-Based Interfaces between network functions
  • Specialized interfaces such as N4 between SMF and UPF

Therefore, an engineer must not assume that every communication path in 5GC is HTTP/2.

Understanding 5G means knowing both the new architecture and where the old engineering rules still apply.

The Complete Service Interaction Model

A simplified 5G registration and session establishment scenario may involve several layers.

UE | | gNB | +---------+---------+ | | N2 N3 | | v v AMF UPF | | SBA | +-------+-------+----------------+ | | | | AUSF UDM SMF NSSF | | | | | PCF | | | UPF | NRF

The architecture is distributed.

The procedure itself may therefore cross multiple logical service boundaries.

This is powerful, but it changes troubleshooting.

Why SBA Changes Troubleshooting

In a traditional EPC environment, an engineer might investigate a signaling path such as:

eNodeB | S1AP | MME | Diameter | HSS

In 5GC, the equivalent operation may involve:

gNB | | NAS / NGAP v AMF | | HTTP/2 v AUSF | | HTTP/2 v UDM | | HTTP/2 v Backend / Data

Now imagine that the IP connectivity between AMF and AUSF is completely healthy.

The problem could still be:

  • Wrong service endpoint
  • Failed NF registration
  • Failed NF discovery
  • Incorrect service selection
  • HTTP/2 negotiation problem
  • TLS certificate problem
  • Authentication or authorization failure
  • Malformed API request
  • Application-level error
  • Backend database problem

The traditional OSI-style question:

“Can I reach the server?”

is therefore only the beginning.

In a distributed 5G Core, connectivity is necessary but not sufficient.

Observing an SBI With Packet Capture

Packet captures remain extremely valuable in 5G.

Suppose an AMF is failing to communicate with an AUSF.

A capture can reveal the sequence:

TCP Connection | v TLS Handshake | v HTTP/2 Setup | v HTTP/2 Request | v HTTP/2 Response | v Application Result

Each stage provides evidence.

If TCP fails, investigate IP connectivity.

If TCP succeeds but TLS fails, investigate certificates, trust, or TLS configuration.

If TLS succeeds but HTTP/2 fails, investigate protocol negotiation and implementation.

If HTTP/2 works but the application returns an error, investigate the service itself.

A successful TCP handshake is not the same thing as a successful telecom transaction.

JSON: Structured Information Inside the Signaling

Another major difference from traditional telecom protocols is the widespread use of structured data representations.

An SBI transaction can carry information represented in JSON.

Conceptually:

{ "subscriber": "...", "session": "...", "service": "...", "parameters": { "type": "...", "policy": "...", "network": "..." } }

The exact fields depend on the service and 3GPP specification.

The important idea is that network signaling increasingly resembles application-layer API communication.

The telecom engineer of the 5G era must be comfortable reading both packets and APIs.

EPC Versus SBA

The architectural difference becomes clearer when the two generations are placed side by side.

EPC ``` Network Elements | v Fixed / Defined Interfaces | v Telecom Protocols | v Signaling Transactions 5GC Network Functions | v Service Exposure | v NF Discovery | v HTTP/2 + APIs | v Distributed Service Calls ```

This is not a statement that EPC was primitive.

EPC was engineered for a different generation of mobile networking.

Its architecture provided enormous scale and reliability.

5GC builds upon lessons learned from that generation while adopting software-oriented architectural principles.

Static Relationships Versus Dynamic Discovery

The contrast can be simplified as:

EPC MME | | "Connect to HSS here" | v HSS 5GC AMF | | "I need UDM service" | v NRF | | "Here are available UDM instances" | +-------> UDM-01 | +-------> UDM-02 | +-------> UDM-03

The second model provides much greater flexibility.

Instances can be added or removed without redesigning the entire logical architecture.

This is exactly the kind of behavior expected in cloud environments.

Scaling the Network

Imagine an operator with increasing registration traffic.

In a software-oriented architecture, additional AMF instances can be deployed.

NRF | +---------+---------+ | | | AMF-01 AMF-02 AMF-03 | | | +---------+---------+ | Subscribers

The same concept applies to other functions.

Additional SMF instances can handle additional session-management demand. Additional UPF instances can provide more user-plane capacity. Additional service instances can be deployed closer to the edge.

This allows scaling to become a software deployment problem rather than simply a hardware expansion problem.

In the 5G Core, capacity can become something you deploy rather than something you physically install.

Failure of a Single Instance

Dynamic discovery also changes how failures can be handled.

Suppose three instances of a function exist:

NRF | +-----+-----+ | | | NF1 NF2 NF3 | | | | X | | FAILURE | | | +-----------+ | Service remains available

The architecture can potentially redirect new consumers toward healthy instances, depending on the deployment and selection mechanisms.

This is one of the strengths of distributed software architecture.

But it also introduces new failure modes.

Redundancy does not remove complexity. It moves complexity into discovery, state management, health, and orchestration.

State Still Matters

It is tempting to assume that service-based architecture means that everything is stateless.

That would be incorrect.

Subscriber sessions, registrations, policies, authentication context, and user-plane state still matter.

The architecture simply distributes those responsibilities across specialized functions.

Distributed State AMF | +---- Registration Context | SMF | +---- PDU Session Context | UPF | +---- Forwarding State | UDM | +---- Subscriber Data | PCF | +---- Policy

This means that troubleshooting must consider both:

  • Service reachability
  • State consistency

A function may be reachable and healthy but still have incorrect or missing state.

The Cloud-Native Connection

The SBA was not designed in isolation from the broader evolution of computing.

Its concepts align naturally with cloud-native principles:

  • Microservices
  • Service discovery
  • APIs
  • Horizontal scaling
  • Dynamic service instances
  • Software-based deployment
  • Automation
  • Observability

This is why 5G Core deployments increasingly use virtualization and containerization.

5G SBA ``` Network Functions | v Software Services | v Containers | v Kubernetes | v Cloud Infrastructure | v Physical / Virtual Hosts ```

The architecture creates the foundation. Cloud-native infrastructure provides the platform on which that architecture can run.

SBA is the architectural bridge between telecom networking and cloud-native software engineering.

What Happens When Discovery Fails?

Consider a practical incident.

The AMF is running. The UDM is running. The network is reachable.

Yet registration fails.

An engineer checks:

AMF ---- ping ----> UDM SUCCESS

It is tempting to conclude that connectivity is healthy and move on.

But suppose the AMF does not know which UDM service endpoint to use.

Or the UDM never registered correctly with the NRF.

Or the NRF contains stale service information.

The result can be:

IP Connectivity YES TCP YES TLS YES HTTP/2 YES NF Discovery NO Service Transaction NO Subscriber Registration NO

This example illustrates why SBA troubleshooting requires an architectural mindset.

The network can be reachable while the service is unavailable.

A Practical SBA Troubleshooting Model

When investigating a failed service interaction, move through the layers systematically.

Subscriber Procedure | v Expected NF Interaction | v NF Registration | v NF Discovery | v Service Endpoint | v IP Connectivity | v TCP | v TLS | v HTTP/2 | v API Request | v API Response | v Application Result | v Subscriber Result

This model prevents engineers from jumping directly into packet-level details without first understanding which service interaction should have occurred.

The right troubleshooting question is always tied to the expected architecture.

Comparing the Engineering Mindset

The EPC encourages a node-and-interface mental model.

“What interface is down?” “What node is failing?” “Which protocol is being used?” “Which gateway is involved?”

The 5GC requires an additional set of questions.

“Which network function provides the required service?” “Did it register?” “Can the consumer discover it?” “Which instance was selected?” “Which service endpoint was returned?” “Can the API transaction complete?” “Is the application-level response correct?”

These questions do not replace traditional network engineering.

They extend it.

The New Telecom Engineer

A modern 5G Core engineer must be comfortable operating across several layers.

Telecom | +-------+-------+ | | Signaling User Plane | | NGAP/NAS GTP-U | v SBA | HTTP/2 / APIs | v IP Network | v Linux / OS | v Containers | v Kubernetes | v Cloud Infrastructure

This is why the role increasingly resembles a combination of:

  • Telecom engineer
  • IP network engineer
  • Linux engineer
  • Cloud engineer
  • Software engineer
  • SRE

The boundaries between these disciplines become increasingly thin.

The 5G Core does not eliminate telecom engineering. It expands the definition of telecom engineering.

Chapter Takeaways

The Service-Based Architecture is one of the defining characteristics of the 5G Core.

Instead of relying exclusively on fixed node-to-node relationships, 5GC network functions expose services that other authorized network functions can consume.

Service-Based Interfaces provide the mechanisms through which these services are accessed.

HTTP/2 is a major transport technology for SBA communication.

REST-style APIs provide structured service interactions, commonly using JSON representations.

The NRF provides network-function registration and discovery capabilities.

Network functions register their capabilities and service endpoints. Consumers can discover appropriate providers dynamically.

AMF, SMF, AUSF, UDM, PCF, and other functions interact through these service-based mechanisms, while specialized interfaces such as N4/PFCP continue to handle specific control relationships.

The biggest architectural difference from EPC is therefore not simply:

“MME became AMF.”

It is:

The mobile core evolved from a network of specialized nodes into a distributed ecosystem of software services.
EPC ``` Nodes + Interfaces | Fixed Relationships | Telecom Signaling | Physical / VM Nodes ↓ 5GC Network Functions | Service-Based Interfaces | Dynamic Discovery | HTTP/2 + APIs | Software Services | Cloud-Native | Distributed Core ```

This evolution brings enormous flexibility.

It also creates new operational challenges.

The engineer must understand service discovery, API communication, TLS, container networking, distributed state, observability, orchestration, and infrastructure — while still understanding the telecom procedures running above them.

The packet is still there. The difference is that now the packet may depend on an entire ecosystem of software services before it is allowed to move.

The next chapter takes the architecture one step further.

If the 5G Core is made of software network functions, the next question is obvious: where does that software actually run?

That question leads directly to virtual machines, containers, Kubernetes, CNFs, networking plugins, Linux networking, and the infrastructure required to turn a cloud platform into a telecom-grade packet-processing system.

The 5G Core is no longer only a network you configure. It is a distributed system you deploy, observe, scale, and operate.
